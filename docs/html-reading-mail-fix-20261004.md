# 每日 HTML 邮件连接修复

## 实际原因

2026-10-04 的实际送达记录显示附件已保存，失败阶段为 Gmail 连接验证。原程序的 Nodemailer SMTP 传输未接入桌面、环境或 Windows 系统代理，直接连接 smtp.gmail.com:465。

本机直连 TLS 超时；通过当前 HTTP CONNECT 代理可得到 Gmail SMTP 欢迎响应。原提示将文件保存和网络连接合并，无法从界面辨别原因。

## 修复

- 发送与“测试连接（不发邮件）”共用代理解析：显式 GSM 网络配置、环境 HTTPS_PROXY / ALL_PROXY、Electron 系统代理，最后才是系统指定的直连。
- HTTP／HTTPS CONNECT 代理支持凭据，凭据不进入界面、送达记录或错误提示；始终验证 Gmail TLS 证书。
- 无效代理和 SOCKS 配置明确报错，不绕过代理偷偷直连。SMTP 当前支持 HTTP／HTTPS，使用 SOCKS 配置时请改为代理软件的 HTTP／混合端口。
- 分别显示附件保存、代理配置、网络超时、Gmail 认证与收件地址错误；只记录经过白名单过滤的代码和 SMTP 阶段。
- 保留已保存附件与既有调度、重试和发送不确定保护。

## 验证

新连接路径在首次真实验证时仍遇到一次临时超时，随后再次验证成功。最终使用临时隔离 Electron 配置和原加密凭据的副本，完成真实 Gmail 连接与认证；没有发送邮件，没有修改原送达记录。脱敏结果位于 output/html-reading-mail-verify-20261004.json。

阅读专项前端 210 项、Electron 代理与送达回归 37 项全部通过；新增覆盖代理优先级、系统代理、解析超时、TLS 保留、认证错误、附件保留和脱敏。生产构建、包体预算、国际化校验通过，根目录 dist 已更新。

全项目类型检查同时发现当前其他 AI 分类结构开发中的两个错误（AIOrganizationPanel.test.tsx 的 purpose 类型与 aiCategoryStructure.ts 未使用导入），与本修复无关，未修改该部分。生产构建另行验证。

## 当前电脑如何生效
