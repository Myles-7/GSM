## 3. Git 策略选择

### 3.1 明确禁止源码树覆盖

源码树覆盖会直接破坏：

- 本地 Store v16 的 Repository Organization 数据。
- server v2、v3 DB migrations。
- Workbench storage。
- Home Sync。
- AGY。
- HTML Reading。
- Custom Discovery。
- 本地部署安全约束。
- 当前 ADR 定义的前端分层。

### 3.2 不在当前 dirty branch 直接 merge v0.8.5

当前工作树存在 150 个 tracked 状态项和大量 untracked 内容。直接 merge 会把三种差异混在一起：

1. v0.8.4 到 v0.8.5 的上游改动。
2. v0.8.4 到当前 HEAD 的已提交个人改动。
3. 当前 HEAD 到工作树的未提交个人改动。

这样的冲突无法清晰归因，也很难按功能域回滚。

### 3.3 不建议 rebase 本地历史到 v0.8.5

本地 Workbench、Repository Redesign、AI Organization 都是跨几十个文件的大提交，与 v0.8.5 在 Repository、Settings、Discovery、Plugin、Store 上高度重叠。rebase 会在多次历史提交中重复解决同类冲突，还会改写已有 recovery 和 delivery 历史。

### 3.4 从干净 v0.8.5 重新搬全部个人功能不是首选

这条路线理论上可行，但要重新搬运大量已经互相集成的 Store、Workbench、Repository Organization、Home Sync、AGY、HTML Reading 和 Custom Discovery。它的行为回归面大于选择性前移 0.8.5 的上游改动。

### 3.5 推荐方法

推荐模型：

当前个人版作为 ours，v0.8.4 作为共同语义基线，v0.8.5 tag 作为 theirs，按功能域做三方语义比较和手工 forward-port。

本次已通过 `git merge-tree --write-tree --name-only HEAD v0.8.5` 做不改工作区的勘探：9 个文本冲突。该结果只针对已提交 HEAD，不包括 Home、AGY、HTML Reading 等未提交工作。

最终建议以分阶段移植结果为期望行为，在干净升级分支或隔离 checkout 中用普通 merge 收口上游 ancestry，逐项核对最终树与已验证结果。不能用 `merge -s ours` 或伪造 Base 的方式仅宣称合并完成。普通 merge 是历史整合工具，禁止的是不分析就覆盖或接受整批 ours/theirs，不是 merge 操作本身。

### 3.6 选择性移植后的长期升级契约

每个上游变更必须标记 applied、adapted、superseded、deferred 或 excluded，记录目标文件、个人实现、测试和取舍原因。deferred 不等于已吸收；存在未处理 High/Critical 项时不能进入正式发布。

历史收口后检查目标提交是结果 HEAD 的 ancestor。若不建立 ancestry，保留真实 Git merge-base=v0.8.4，另记录 consumedUpstreamCommit=v0.8.5 及完整消费清单；下一次分析从消费基线取上游变化、从真实历史取个人变化，不能混用两者。

## 5. PR #418：Repository identity，迁移第一阶段

### 5.1 上游修复的问题

旧 Batch Star 路径可能为新增 repository 生成时间戳或 synthetic ID。后续从 GitHub 同步时返回真实 repository ID，Store 于是把同一个 full_name 当成另一条记录，导致本地 AI summary、AI tags、category 等数据丢失。

#418 新增 src/utils/repositoryIdentity.ts，并建立以下不变量：

1. 新数据使用真实 GitHub repository ID。
2. full_name fallback 只给历史 synthetic ID 自愈使用。
3. 批量匹配分两遍：先精确 ID 占用，再一对一 legacy name fallback。
4. 普通真实 ID 记录不能仅凭同名被合并。
5. 已有权威真实 ID 的 rename 加 old-name reuse 场景，不会仅因旧名称相同把两条仓库的数据串在一起。

上游 helper 包括：

- SYNTHETIC_REPOSITORY_ID_FLOOR = 1e11。
- isValidGitHubRepositoryId。
- isLegacySyntheticIdRecord。
- matchesSameGitHubId。
- matchesLegacyNameFallback。
- findIdentityMatch。
- assignIdentityMatches。

### 5.2 当前项目的冲突点

当前：

因此不能覆盖 upstream repositorySlice.ts。

### 5.3 推荐实现

先完整引入 identity utility 和对应测试思想，再把所有把 GitHub repository 合入本地 repositories 的入口统一到同一 identity contract：

- full sync。
- batch Star。
- Discovery Star。
- Search 和 Import。

- custom description。
- AI summary、AI tags、AI details。
- category、category lock。
- subcategory。

### 5.4 个人版必须补齐的身份迁移协议

本地 `addRepository` 仍按 full_name 找已有项并保留旧 ID；新增记录的 synthetic ID 由 Store 产生，不能只改 Batch Star hook。`mergeStarredRepositories` 以及 `repositoryMerge.ts` 只按 ID 匹配；Home 服务端 `taskRefreshStars.ts` 按真实 ID 查 canonical record，同名 legacy record 会被留下并标成 unstarred。四条路径均需专项处理。

上游 helper 只判定身份，不会迁移引用、清理所有重复记录或提供跨库事务。`isValidGitHubRepositoryId` 只检查正整数，`1e11` 是区分历史时间戳 ID 的启发式阈值；需要输入验证、重复 ID 检测和冲突策略，不能将阈值称为永久 GitHub API 保证。

还存在信息论上的限制：legacy record 没有真实 ID，而旧 full_name 已被另一仓库复用时，仅凭当前同名 GitHub 响应无法证明它就是原仓库。上游按名称自愈是 best-effort，不是所有 rename/reuse 场景的零误合并保证。结合可用历史元数据与 canonical 证据排除冲突；无法确认时保留旧记录并进入 dry-run 审核，不能把“唯一同名候选”直接写成“身份已证实”。

建议先建立 owner/workspace 限定的 dry-run 计划，列出 `{ oldId, newId, fullName, matchReason, affectedReferences }`。分类为唯一可确认、已存在 canonical record、同名多候选、无权验证、已 tombstone 五类；歧义项保留原数据并报告，不自动猜测。

| 引用域 | 实际入口与处理要求 |
| --- | --- |
| 主 Store、账户工作区 | repositories、repositoryOrder、releaseSubscriptions、releases[].repository.id、searchResults、运行中 selection；仅将仓库 ID 改映射，不能改 Release 自身 ID 或 category ID |
| Workbench / Organization | `repositoryChatStorage.ts` 的 sessions.repoId、projects.repositories，以及 proposal.organization.entries[].repositoryId；保留历史证据与操作结果，不用字符串替换所有数字 |
| Home SQLite | sync_v2_records、canonical repositories、subscriptions、organization；通过同一 SQL transaction 重键并生成可同步变化，不直接改业务表而绕过版本/cursor |
| Home IndexedDB | `src/home/database.ts` 的 records、shadow、outbox、meta；旧 key 的未确认操作不能简单重写 ID 后以原 opId 重发 |
| Discovery / Vector | custom channel 的已读仓库 ID、相关 edition/candidate 缓存，以及向量记录 ID、content hash、active generation；仅处理明确属于该身份的关联 |

主 Store、Workbench IndexedDB、Home IndexedDB 和后端 SQLite 之间没有单一 ACID transaction。需要带步骤状态的迁移 journal、幂等操作和启动恢复：暂停对应 owner 的同步与新写入，备份并预览，在单库内事务执行，校验所有引用后解除暂停。中途退出时继续或恢复到完整旧状态；禁止把“Store 更新成功”当作全链路成功。

Home 模式以 server canonical identity 为权威，并考虑未更新手机仍携带 oldId/outbox 的情况；设计有期限的 oldId alias 或明确客户端升级屏障，防止旧记录被重新创建。alias 只用于已确认 legacy mapping，不能开放为任意同名合并。新旧记录均有个人字段时，保留明确编辑与锁定状态、记录差异；空值代表主动清空，不能用 `||` 随意填回旧值。

纯 Store migrate 不应联网请求 GitHub 或启动付费任务。真实 ID 需由后续已授权的正常同步确认，数据 shape migration 与身份修复是两个步骤。

### 5.5 必测场景

至少覆盖：

1. Batch Star repo 使用真实 GitHub ID。
2. legacy synthetic 加相同 full_name，自愈为真实 ID，AI 和 category 不丢。
3. repository rename。
4. rename 后旧 full_name 被另一个真实 ID 仓库复用。
5. 同批输入中 ID match 优先于 legacy name fallback。
6. category、subcategory、repositoryOrder 引用不悬空。
7. release subscription 不丢。
8. Workbench 和 AI Organization 对 repository scope 的引用仍可解析。
9. 重复同步幂等。

其它 Batch Star UI 功能必须在 identity 修复之后再合。

- XML Content-Type 和响应文本不被 JSON 化。

### 12.5 生命周期与个人 AI 工作流的集成

iframe 的 `sandbox="allow-scripts allow-same-origin"` 依赖 plugin-page 与宿主不同来源、无 Node 集成，以及 protocol/CSP 限制。必须以实际 Electron 浏览器验证，不能只用 jsdom 构造 MessageEvent 宣称来源安全。

账号切换、登出、插件禁用/卸载、页面导航和 modal 关闭时清除 session/token；忽略迟到 README/AI 回调，不能将前一账号上下文发给新页面。每次 opensPage 重新建立 session，旧 requestId/token 不可重放；README 更新与 iframe onLoad 次序需覆盖。

本地 `pluginClient.ts` 已通过 aiTaskJournal 跟踪 Worker 操作，并校验账号变化。新页面 AI 调用也需保留当前 usePluginAI/AGY 的任务记录、并发限制和用户逐次确认，不因 Worker-less 而绕过它们。clipboard image 和保存文件遵守权限与用户保存对话框，失败和取消不等于成功。

上游普通请求预算为 1 MiB，binary args 预算为 10 MiB 的 JSON/base64；编码后的 10 MiB 不等于原始图片允许 10 MiB。renderer 与 Node 采用相同 UTF-8 byte 口径；对非 ASCII README、超长 base64、不可解码图片及文件名边界补测试。示例插件生成的 HTML 必须保留内容净化规则，不能仅依赖 AI prompt 要求“无脚本”。

## 15. Store 是全迁移最高数据风险点

### 15.1 当前事实

当前：

src/store/persistence/options.ts -> version 16

上游 v0.8.5：

src/store/persistence/options.ts -> version 16

但两个 version 16 的 schema 已经不是同一个 schema。

当前个人版持久化并 normalize：

- subcategories。
- subcategoryOrder。
- repositoryOrder。
- pageTranslationEnabled。
- Repository Redesign 的组织语义。

上游 v0.8.5 的同版本状态包含以下字段和行为，其中旧翻译字段沿用历史定义，并非本次新增：

- external discovery channels normalization。
- translationEngine。
- autoTranslateRepoDescription。
- scrape support 相关 channel normalization。

如果直接合并仍保留 version 16，Zustand 没有版本跳变可触发，旧用户的 persisted snapshot 可能被新的 merge 和 normalizer 静默重解释。

准确说法：`migrate` 在数字版本不匹配时调用，`merge` 在同版本 hydration 时仍运行；可加字段或保持原 normalizer 不会仅因 version 相同自动损坏数据。当前个人 normalizer 会丢弃非 built-in 的 discoveryChannels，替换成上游 normalizer 又可能丢个人组织字段，这才是已定位的具体危险。上游旧翻译字段不是 v0.8.5 新增能力，不应把“上游一直保留”写成“本次新增或恢复”。

### 15.2 本次建议契约：下一持久化版本为 17

迁移 v0.8.5 的第一批 persisted Store 改动必须：

1. 实施前复核实际版本，当前计划为 version 16 -> 17；数字用于 schema，不与应用 0.8.5 版本混同。
2. migrate 保持 idempotent 和 total。
3. 以当前个人版 v16 为输入契约。
4. 保留当前全部 Repository Organization 字段。
5. 保留 pageTranslationEnabled。
6. 继续删除退休 translationEngine 和 autoTranslateRepoDescription。
7. 添加 external discovery channel 的 normalization。
8. 对 selectedDiscoveryChannel 在被删除或无效时做安全 fallback。
9. discoveryRepos 继续不得进入 persistence。
10. 更新 modularization contract tests。

Phase 1 若提前发布或交付 v17，必须已纳入最终 external feed 的数据类型、partialize、migrate 和 merge/normalizer，而非仅放一个未使用 helper。Phase 5 后来又改变持久化解释时，应按实际 schema 再升到 18 并补 v17 fixture；不能坚持“全升级只能升一次”而绕过迁移。若 v17 始终只在隔离分支使用，可在首次发布前收敛为同一个最终契约，并保持所有已经产生的测试快照可读。

高于当前支持版本的备份或数据不能强行降级 normalizer 后写回，应给出拒绝/只读说明。其他存储分别有自己的版本：Workbench IndexedDB v2、Custom Discovery IndexedDB v1、Home records/outbox，以及 server migration v3；没有结构变化不应空升版本，有变化必须单独写迁移。

### 15.3 迁移测试必须用历史 snapshot

至少准备：

- 纯上游 v0.8.4 snapshot。
- 当前个人版 v16 snapshot，含 category、subcategory、manual repository order。
- 当前个人版 v16 snapshot，整页翻译开启。
- 含 legacy synthetic repository ID 的 snapshot。
- 主 Store snapshot 与独立 Custom Discovery IndexedDB fixture 的组合，不能假设 custom 数据位于主 Store。
- 含 external discovery channel 的新 v17 snapshot。

每个 snapshot 都要验证：

- hydrate 不抛错。
- migration 重复执行结果相同。
- category、subcategory、order 不丢。
- AI 数据不丢。
- pageTranslationEnabled 不变。
- retirement fields 不复活。
- external channel 能保留。
- discoveryRepos 仍未持久化。

## 16. 服务端数据库与配置不可被上游覆盖

当前项目服务端已经拥有 v1、v2、v3 migrations 和更丰富 schema。上游 v0.8.5 没有这些本地演进。

7. WebDAV server proxy 只合 route 语义，不改变当前数据库版本链。

server/src/config.ts 当前包含本地更严格的安全和部署行为，例如 API_SECRET、HOST、DATA_DIR、ENCRYPTION_KEY_FILE 等。保持现有本地安全语义。

## 22. 数据安全与回滚

### 22.1 代码恢复点

迁移前建立：

- codex/upgrade-upstream-v0.8.5。
- recovery/pre-v0.8.5。

每个 Phase 形成可审查的提交组，跨层协议以完整组合交付。推荐提交边界：

1. migration: establish v17 persistence and repository identity
2. fix: forward-port WebDAV and desktop markdown stability
3. feat: add token permission guidance and batch star history
4. fix: forward-port release asset filter matching
5. feat: add external discovery feeds alongside custom discovery
6. feat: upgrade plugin pages to v1.4 modal actions
7. feat: add appearance settings and vector indexing status
8. build: slim desktop package with local runtime closure
9. ci: reuse desktop web bundle across platforms，可选
10. migration: reconcile upstream ancestry and validate personal release

如果一个阶段失败，先暂停写入与同步，识别代码失败还是数据解释已变化，再选择修复向前或配套恢复。不能只撤销 commit 后用旧程序打开已迁移数据，也不要 reset 掉后续未提交用户工作。

### 22.2 SQLite

迁移前：

- 应用和 backend 正常退出后再做文件级副本。
- 更优先使用 SQLite online backup，确保 WAL 已包含。
- 记录 integrity_check。
- 记录 schema version。
- 记录关键表 row counts。

迁移后验证：

- 旧 v3 DB 打开是 no-op 或只执行明确新增 migration。
- fresh DB 可以完整升级。
- Repository Organization 列仍存在。
- Sync V2 和 task 表仍存在。
- row counts 没有非预期下降。

SQLite 在线 backup 只保证单个数据库快照一致，不保证与 IndexedDB、Store 或远端 Home 同一时刻。需暂停所有写入方并记录共同恢复点；对活动 WAL 数据库不可只复制主文件。恢复时先隔离旧手机、任务执行器和 outbox，防止恢复后再次重放新版本写入。详见 [SQLite 官方备份说明](https://www.sqlite.org/backup.html)。

### 22.3 IndexedDB 和桌面 origin

v0.8.4 升级已经出现过一个真实问题：开发端口从 5174 变成 5173 后，IndexedDB 因 origin 改变看起来像数据丢失。

本次迁移必须继续固定现有桌面开发 URL 契约，尤其是原快捷方式对应的 127.0.0.1:5174。

不要把端口变化误诊为 migration failure，也不要因为看见空 Store 就立即初始化覆盖原数据。

### 22.4 Secrets

备份或验收时不得把以下内容提交 Git：

- GitHub token。
- Backend API secret。
- AI API keys。
- WebDAV password。
- Gmail app password。
- X auth Cookie。
- RPC secret。
- AGY 私有路径配置。

## 25. ADR 0001 对迁移的约束

## 27. 冲突处理决策表

当 Codex 遇到冲突时，按以下规则判断：

| 冲突类型 | 默认决策 |
| --- | --- |
| 上游修 bug，本地无等价修复 | 吸收上游行为 |
| 上游新增功能，本地无对应功能 | 按当前架构适配吸收 |
| 上游新增功能，本地已有更强但不同能力 | 共存，明确 namespace 和职责 |
| 上游删字段，本地仍使用 | 保留本地，除非完成显式 migration |
| 上游 Store version 与本地相同但 schema 不同 | 判断个人实际解释是否变化；本次需建立下一版本，不以数字相同直接判断损坏 |
| 上游 DB schema 比本地旧 | 保留本地，只增不减 |
| 上游安全校验比本地严格 | 默认吸收严格校验 |
| 上游 UI 重组，本地有额外 tab | 做 union，不覆盖 |
| 上游 package slimming 删除本地 runtime dependency | 保留 runtime dependency |
| 上游翻译体系与本地整页翻译冲突 | 保留本地整页翻译 |
| 上游 external Discovery 与本地 AI Custom Discovery | 两者并存 |
| 上游 Plugin V1.4 与旧 page bridge 冲突 | 升级协议，不降低 origin 安全 |

## 28. Codex 开始迁移前的预检命令

开始任何代码改动前，记录：

    git status --short --branch
    git rev-parse HEAD
    git rev-parse v0.8.4
    git branch --show-current
    git diff --shortstat v0.8.4
    npm --version
    node --version

如果本地已经具备 v0.8.5 tag/ref，再记录：

    git rev-parse v0.8.5
    git merge-base HEAD v0.8.5

如果本地 ref 仍旧，使用固定 tag SHA 245ee3107e8a2ba849ee6e04ffdd920d6e35ecea 获取，不跟随 main。

建议为每个高冲突文件做三方比较：

    git show v0.8.4:path/to/file
    git show HEAD:path/to/file
    git show v0.8.5:path/to/file

这里 HEAD 只代表已提交个人实现；本次审计工作区仍有大量 dirty changes，必须同时阅读实际文件。Phase 0 冻结后改用 personalCheckpoint 作为三方比较中的个人输入，避免漏掉未提交功能。

当前工作树另有未提交变化时还要单独读取工作树文件；不要把 HEAD 内容误当成当前用户正在开发的版本。

## 32. 最终建议

1. 先保护当前工作树和真实数据。

这一顺序降低把现有数据置于不可恢复状态的风险，但不构成零风险保证；跨存储身份迁移、未升级客户端和不完整备份仍需实际恢复演练。
