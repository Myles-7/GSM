# 真实全库整理：修复与验证记录

## 验收目标

- 原账号全库 369 个仓库，用途、技术两套分别至少 351 个有效归属。
- 其余仅允许有证据的疑难项；基础设施失败、待处理及旧位置兜底不计通过。
- 不自动应用分类，不修改收藏、Lists、个人描述或标签。
- 小样本上限 20 次调用；全库追加上限 234 次，累计台账跨重启保留。

## 已核实的问题

- 原任务归属阶段最早五次请求在输入交付后超时，随后排队超时扩散。不能把二者都解释为模型未启用。
- High 的 effort 兼容性问题与独立 Medium 模型不是同一件事。用户明确允许隔离切换 Medium，生产默认配置不变。
- 本机 AGY 可执行文件在运行期间变更；隔离副本重新检测、测试后继续，没有绕过文件身份校验。
- Medium 的小连接探测可以成功，而真实分类负载仍可能超时。连通性成功不代表全库分类稳定。
- 系统提交内存曾不足 1 GiB，导致类型检查内存分配失败；这与模型超时是独立证据，不据此推断所有超时原因。
- 真实请求 #90 在约 179.65 秒已返回终止结果，但进程随后退出，旧 180 秒总计时仍丢弃结果。改为初始化、生成及结果后退出分别计时；仍须协议校验与确认退出才接受结果。
- 第 102 次调用附近再次发生系统内存分配失败：PowerShell 报 `System.OutOfMemoryException`，验证渲染进程随后崩溃。两套各 240 项检查点保留，资源恢复后改用单并发续跑；不将此问题解释为分类格式错误。
- 隔离小样本浅合并曾残留旧 `error` 字段；按相同验证指纹、目标及理由核对后清理当前错误，历史错误台账保留。

## 关键修改

- 分类 ID 短引用、紧凑分类元组与事实摘录；按输入体积拆批，保留已接受归属和人工目标。
- 请求派发跟随实际执行槽；排队与生成分别计时，未发出请求不计模型尝试。
- 公共故障采用有界恢复探测及暂停，不把相同故障不断传播到其余仓库。
- 请求预算、原批次预算及定向修复有界；账号、停止与迟到输出保护保留。
- 真实有效归属与疑难项分别展示，零有效归属不再标为成功；历史错误不单独决定新任务结果。
- 有显式结构校验器时优先采用经过校验的结构结果，仍保留单轮与工具调用安全限制。

## 最终真实验证（全库草案门槛通过，未应用）

- Medium 十仓库小样本：用途 10/10、技术 10/10，包含资料不足项的真实 README 补充；未应用。
- 小样本台账共 20 次 CLI 调用。一次隔离 JSON Schema 实验触发多轮内部行为，不能把 CLI 次数宣称为精确的底层模型请求数；该实验已禁用，未用于全库。
- 缩批验证发现快速流水线会覆盖外部传入的批次划分；增加显式归属批次上限，补充接续不重发已接受行的回归测试。
- 全库使用获授权的 Medium、三仓库小批次及最多两路派发；资源不足时保留检查点并改为单并发，资源恢复后继续。最后三个空结果失败仓库拆成单仓请求后全部成功。
- 全库累计 154 次 CLI 调用，包含失败、重试和初始化未完成项，低于 234 次追加预算；台账跨进程重启累计，未擅自换模型。
- 369 个仓库全部获得处理结果，无基础设施失败、无待处理项。严格审核后的用途有效归属 369/369（100%），技术有效归属 361/369（97.8%），两套均高于各 351 项门槛。
- 技术方案的 8 项纯资料、模板或资源索引仓库缺少明确工程技术栈，单独列为待确认、不默认勾选、不计有效归属；保留原位置不用于凑数。
- 按类别抽查 11 个代表仓库，并检查全部疑难项。另按原始描述和保留资料校正 `commaai/openpilot` 的用途草案：由移动应用改为 AI 主类，暂不指定二级，明确记录为审核修改；不冒充原模型输出、不改已有人工目标。
- 单批耗时仍波动明显，出现过超时与无有效内容的成功终止消息；本次通过不代表 AGY 从此不再超时，也不宣称固定提速倍数。
