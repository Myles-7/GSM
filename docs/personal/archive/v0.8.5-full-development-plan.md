3. P1-08：建立 owner/workspace 隔离的 oldId -> realId dry-run。先处理精确 ID 再处理 legacy 名称，输出冲突、不确定项和孤儿引用；`1e11` 只是历史 ID 启发式，不是 GitHub 永久上限。
4. P1-09：没有可信真实 ID 时不伪造 canonical。纯 Store migrate 不发 GitHub/AI 请求；由应用层或 Home 权威同步获取必要元数据，再协调迁移。
5. P1-10：新旧数据都有编辑时保留人工值、锁和来源，冲突进入可审计队列；空值若代表主动清空，不用 `||` 自动补旧数据。非映射字段不得重写。

单一同名候选不等于身份已证明：legacy 没有真实 ID 时，无法仅凭当前 GitHub 同名响应排除旧名称复用。dry-run 应区分上游 best-effort name match 与有 canonical/历史证据的确认映射，存在矛盾或不确定性时保留旧数据供审核；不能承诺所有 legacy rename 场景都自动无损自愈。

### 4.4 P1-C：跨存储 journal 与同步协议

| 参与方 | 必须处理的引用 | 验收要点 |
| --- | --- | --- |
| AppStore/accountWorkspaces | repositories、repositoryOrder、releaseSubscriptions、releases[].repository.id、搜索结果/selection | 不修改 Release 自身 ID、分类 ID 或其他同值数字 |
| Workbench IDB | sessions.repoId、projects.repositories、proposal.organization.entries.repositoryId | 会话、项目范围和待执行建议指向同一仓库 |
| Home server | canonical records、organization/subscriptions、SQL 镜像、tombstones | 同名 legacy 不残留为另一 unstarred 仓库，删除语义不复活 |
| Home IndexedDB | records、shadow、outbox、meta | key、payload 和游标一致；已确认 opId 不重用为不同操作 |
| Custom Discovery | 读状态、candidate/edition 内仓库引用 | edition 与用户已读行为不丢 |
| vector | repo key、content hash、activeIndex/generation | 旧 key 失效，按正确 namespace 重建，不混入其他账号 |

1. P1-11：在应用协调层建立 durable journal，记录 input fingerprint、映射版本、参与方、已完成步骤、备份标识和失败原因；每步本地事务可幂等重放。不要宣称跨 SQLite/IDB/Zustand 存在单一 ACID 事务。
2. P1-12：迁移期间暂停新写入与同步，显式提示维护状态；全部参与方验证通过后再放开。中断重启只执行未完成或可幂等步骤，数据不确定时只读并恢复，不自动“初始化空库”。
3. P1-13：Home server 为 canonical 权威。优先采用受限、带 owner 与映射来源的 legacy alias，加最小客户端版本/迁移屏障；如现有协议无法安全解析 oldId，先阻止旧客户端写入并完成升级，不猜测重放。
4. P1-14：处理未 ACK 的旧 outbox：服务器若已接受原 opId，不能将 payload 改成新 ID 后以原 opId 再发。对未接受操作采用明确迁移/撤销/新操作协议，记录顺序和 ACK 对应关系。
5. P1-15：只有需要 SQL schema 时才追加 v4 等 forward migration，不改历史 v1/v2/v3。仅 JSON 数据变化可用数据迁移，但也须有独立版本和 journal。

### 4.5 验收、交付与恢复

专项覆盖真实 ID、legacy 自愈、rename、old-name reuse、两个账号同名、一对一映射、重复 ID、主动清空、锁字段、tombstone、二次 sync、跨库引用审计。故障注入覆盖每个 journal 步骤前后、应用崩溃、服务不可达、手机迟到操作与丢 ACK。

交付为完整 schema/normalizer、identity utility 与各入口适配、journal 协调、Home 兼容策略、历史 fixture 和副本 dry-run 结果。退出条件是字段保留、引用一致、无不解释重复记录、恢复可续跑；存在不确定映射时隔离这些记录，不静默丢弃。

恢复必须先暂停所有客户端和任务，再共同恢复关联数据或执行经验证的逆映射；撤销代码提交本身不恢复 IDB/SQL。不能让旧客户端与新 server 在恢复途中继续写入。

## 5. Phase 2：WebDAV 与基础稳定性

### 5.1 P2-A：三层 WebDAV transport

范围：`electron/main.js`、preload、electronProxy、backendAdapter、webdavService、`server/src/routes/proxy.ts` 及测试。当前 route 已存在，做差量适配，不替换本地 AGY/HTML Reading/MCP/Sync V2 实现。

1. P2-01：集中选择 Electron IPC > backend proxy > browser direct；业务层保持一个 WebDAV 入口，不在组件散落 transport 条件。
2. P2-02：IPC 输入类型、主 frame 来源、请求所有权和 preload exposure 一并测试；若需要 undici，显式加入并锁定兼容依赖，不能依赖偶然的传递安装。
3. P2-03：现有 backend 安全 configId 保持通常请求优先，但编辑连接测试采用明确 inline test 模式，实际测试未保存的新地址/密码。
4. P2-04：校验 HTTP(S)、方法、路径和最终目标 URL，保留 NAS 私网需求；公共 feed 不能复用 allowPrivate=true。处理 redirect/Authorization，错误日志脱敏。
5. P2-05：timeout 在 1,000 至 300,000 ms 内规范化，raw XML/Content-Type 保留，204/304/HEAD 不生成错误 body。
6. P2-06：定义 renderer 取消语义并贯通可安全取消的 IPC/backend/direct 请求；若 main 不能真正取消，至少停止迟到 UI 更新和重试，并明确限制。未知 PUT/DELETE 结果不无条件重试。

验收四种环境组合：Electron 无 CORS、Browser 有 backend 无 CORS、Browser 无 backend 有 CORS、Browser 无 backend 无 CORS 清晰失败。覆盖 PROPFIND 207/XML、GET/PUT/DELETE、项目支持的 MKCOL、inline 编辑、timeout/取消/非法 header。HEAD 可达不等于 DAV 写权限通过。
