# P0.2.0 身份迁移与共同恢复

本说明对应选择性移植，不代表完整消费上游 v0.8.5。应用版本仍为 0.8.4。原用户数据不因代码开发或测试自动迁移。

## 执行前

1. 正常退出其他 GSM 桌面、网页和同一向量 namespace 的写入客户端。暂停后台 AI、分类、同步及索引任务。
2. 保留代码恢复点及一致的数据备份。源码回滚不能撤销 IDB、Home canonical 或 Vectorize 中的重键。
3. 在设置的仓库身份面板运行 dry-run。只有可核实的原仓库身份或明确人工确认才选择映射。单一同名候选不证明身份，rename、旧名复用和歧义不会自动合并。
4. 有 Home 时先完成原 outbox、原 payload/opId 和任务请求的确认。丢 ACK 不得通过修改旧请求并生成新 ID 来解决。
5. 已使用向量的账号需要部署本次随代码交付的 Worker 产物。旧 Worker 缺少 identityStorage/identityRestoreCheck 时明确阻止迁移；不自动替换远端引擎、配置或部署。

## 存储边界

| 存储 | 处理 |
| --- | --- |
| 主 Store | v16→v17 的 external 配置契约；确认后修仓库、排序、Release 仓库引用、订阅和运行时视图 |
| Workbench | 账号限定的会话、选定仓库、项目、待执行操作/组织草案；已执行操作及历史证据不改 |
| Custom Discovery | 原独立存储不搬迁；可变 read/blocked/recommended/cache 引用修复；历史 editions 不改；未使用账号跳过 |
| Home | canonical 原子事务、旧 ID tombstone、映射、服务器 journal；旧 ID/嵌套引用迟到写入明确冲突 |
| Vectorize | 在原 active generation 备份、copy、验证、delete；不接触其他 generation |

迁移不是跨数据库 ACID 事务。日志在各参与者写入前持久化输入，在确认后登记完成步骤；中断后同账号、同工作区、同 journal 续跑。页面重载仍受持久维护标记约束。

## 中断与恢复

- 优先使用“继续迁移”，不能修改原映射、服务器输入指纹和请求身份后直接重发。
- 服务端恢复在事务中区分 apply 已提交但丢 ACK、apply 未发生和后续修改。未 apply 的恢复登记终态取消证据，拒绝迟到原 apply。
- 显式共同恢复前先冻结并排空本机写入，检查 Store/参与者前后指纹及远端向量可恢复性；服务器再检查 postHash。后续编辑、删除、账号、namespace 或工作区变化都导致冲突，不覆盖。
- Store 恢复仅覆盖当前账号参与身份迁移的字段，不把其他账号和全局偏好倒回旧快照。
- 部分恢复发生中断时保留冻结和 journal，继续恢复会重用原备份和已确认的服务器终态。先恢复到可确认状态，再恢复 Home 投影和常规写入。
- 如果恢复因后续编辑被拒绝，保留新的数据和原备份。不得绕过校验强制覆盖；需要人工协调。已完成迁移的失败恢复可用继续入口解除冻结，保留迁移后的数据。

Vectorize 没有跨客户端原子 CAS。本地门禁和服务端批次重查不能替代停止其他 namespace 写入方；任何已开始的远端写入或文件保存都可能在取消后完成。这里不声称取消就是撤销。

## 备份位置

迁移前恢复点在 `D:/桌面/GSM-recovery/pre-P0.2.0-20261002`。含 userData、服务器/Home 一致 SQLite 快照及必要秘密材料，不提交、不公开，也不在测试中自动读入原 profile。恢复应与当前工作区、账号、origin、应用身份和加密材料一并核对。
