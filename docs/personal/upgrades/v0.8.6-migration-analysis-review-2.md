## 1. 首次发现

### 1.1 分片字段重复会在模块加载期直接抛错——按 §5.4 表格实现会开不了机

上游 `src/store/persistence/shards.ts` 在构建 `FIELD_TO_SHARD` 映射时有一段防御：

```js
if (FIELD_TO_SHARD.has(field)) {
  throw new Error(`[persistence] field "${field}" is assigned to more than one shard`);
}
```

而报告 §5.4 建议的 `organization` shard 字段是：

```text
classificationSchemes, customCategories, hiddenDefaultCategoryIds, categoryOrder,
subcategories, subcategoryOrder, repositoryOrder, defaultCategoryOverrides
```

实测这 8 个里有 **4 个已经存在于上游 `core` 的字段清单中**：

| 冲突字段 | 在上游 core | 在报告 organization | 结果 |
| --- | --- | --- | --- |
| `customCategories` | ✓ | ✓ | 重复 |
| `hiddenDefaultCategoryIds` | ✓ | ✓ | 重复 |
| `categoryOrder` | ✓ | ✓ | 重复 |
| `defaultCategoryOverrides` | ✓ | ✓ | 重复 |

（实测确认：这 4 个字段在上游 `shards.ts` 中各出现 2 次，分别在 `PERSISTENCE_SHARD_FIELDS.core` 与 `WORKSPACE_REFERENCE_FIELDS`。）

**后果：** 若实现者照着 §5.4 表格把字段加进 `organization`，却保留上游 `core` 原样，`FIELD_TO_SHARD` 会在模块初始化时 `throw`，应用在启动前就崩溃。

这不是静默数据丢失——它是**响亮失败**，反而安全。但它会以"莫名其妙开不了机"的形式出现，而不是"分片配置有误"。

**修正做法：** 把这 4 个字段从 `core` **移出**再加入 `organization`，使 `PERSISTENCE_SHARD_FIELDS` 满足全局唯一。并在 Phase 1 补一条断言，覆盖全部 partialize 字段（而非仅 `AccountWorkspace` 字段），要求每个字段恰好落入一个 shard。报告 §5.7 已经为 `AccountWorkspace` 提出了这条测试，但没有意识到**同一个 invariant 在 shard 层也存在且会炸得更早**。

### 1.2 `core` 里住着两个无界增长数组，违背 core 分片的设计前提

#424 的核心前提是"`core` 体积小、写一次只有几 KB"。但上游 `core` 里有两个**随使用无限增长**的数组，且报告 §5.4 原样继承了这一布局：

```text
core: [ ... 'releaseSubscriptions', ..., 'readReleases', 'readForks', ... ]
```

对照 GSM `src/store/persistence/options.ts`，这两个字段确实被持久化：

```js
releaseSubscriptions: Array.from(state.releaseSubscriptions),
readReleases: Array.from(state.readReleases),
readForks: Array.from(state.readForks),
```

`readReleases` 是"读过的 Release ID"累积集合——对长期使用的 Stars 管理器，它随订阅仓库数和更新频率单调增长，且**永不清零**。它被放在每次 UI 偏好变更都要重写的 `core` 里，恰恰复现了 #424 想要消灭的那个病态：**改一次主题，就要重新序列化几 MB 的已读状态**。

报告敏锐地发现了 `classificationSchemes` 会掉进 core 的性能陷阱（§5.3），却漏掉了上游自己放进 core 的这几个无界集合。

**建议：** 在 Phase 0.5 的 byte-size 度量中，把 `readReleases` / `releaseSubscriptions` / `readForks` 一并计入并以真实数据测量。若确实已具规模，为其单独建 `readState` shard（它们都是 Set→Array，天然适合引用判脏且与 releases/forks 生命周期独立）。

### 1.3 采用上游 `redact.js` 会造成 4 项脱敏能力**倒退**——GSM 现有实现更强

这是本轮最严重的发现，且方向与报告的假设相反。

报告 §3.5 / §9.3 的立场是"上游脱敏是基础，GSM 需要**补充** AGY/SMTP/RPC 等域"。但实测对比显示，在四类规则上 **GSM 现有 `src/utils/logSanitizer.ts` 严格强于上游 `v0.8.6:electron/redact.js`**：

| 规则 | GSM 现有 `logSanitizer.ts` | 上游 `redact.js` (v0.8.6) |
| --- | --- | --- |
| 细粒度 PAT `github_pat_...` | ✓ 覆盖（第 152 行） | **✗ 实测不存在** |
| 其他 token 前缀 `gho_/ghu_/ghs_/ghr_` | ✓ `gh[pousr]_[a-zA-Z0-9]{20,}` | **✗ 仅 `ghp_[a-zA-Z0-9]{36}`** |
| 键值对形态 `password=xxx` / `api_key: xxx` | ✓ 第 153 行专门规则 | **✗ 无对应规则** |
| PEM 私钥块 `-----BEGIN PRIVATE KEY-----` | ✓ 第 155 行整块剔除 | **✗ 无** |

（验证方式：`git show v0.8.6:electron/redact.js | grep -n "github_pat\|gh\[pousr\]\|PRIVATE KEY\|\\s\*\[:=\]"` → 仅命中 URL 参数清单，**四条规则一条都没有**。）

**后果：** 报告 §9.2 建议吸收上游 `redact.js` / `netTap.js` 作为诊断模块。若照做，`netTap.js` 内部 `const redact = require('./redact')` 会把每一次 capture 到的 body/stack 交给这份**覆盖面更小**的脱敏器，于是：

- 出错栈里内联的 `github_pat_` 令牌不再被剔除；
- 日志正文里的 `password=...` 形态不再被剔除；
- AGY / 本地 Agent / CLI stderr 里若出现 PEM 私钥块，不再被整块剔除。

也就是说，**"提升诊断能力"这一步会顺手降级 GSM 既有的脱敏强度**——而这恰恰是报告第 0.3 节"安全冲突"表里明文规定不允许发生的事（"本地更严格的安全不变量不因上游功能升级而回退"）。报告自己在 §3.3 为插件 V1.4 逐条列了 10 项本地优势，但对诊断域没有做同等的双向对比。

**修正做法：** 以 GSM `logSanitizer.ts` 为唯一真源，向主进程移植时**导出 GSM 的四条规则**，而不是**导入**上游 `redact.js`。`netTap.js` 只需改为依赖这份更强的实现。

### 1.4 反向问题：同一条正则既存在于 GSM 又把诊断 bundle 变成"无名姓的气氛证据"

GSM `logSanitizer.ts:19` 与上游 `redact.js` 用了**完全相同**的通用密钥正则：

```ts
const GENERIC_SECRET_RE = /^[a-zA-Z0-9+/=_-]{20,}$/;   // 两边一致
```

且 `sanitizeForLog` 会把这条规则作用于走查到的**每一个字符串节点**。实测：

```text
MASKED  AmintaCCCP/GithubStarsManager   ->  ***ager
MASKED  microsoft/typescript            ->  ***ript
MASKED  0123456789abcdef0123456789abcdef01234567  ->  ***4567
MASKED  owner/repo/status/commit_activity  ->  ***vity
keep    vercel/next.js          (含'.'，未被匹配)
keep    torvalds/linux          (长度不足)
```

即：**任何长度 ≥20、只含 `[a-zA-Z0-9+/=_-]` 的字符串都被当作密钥抹掉末尾四位**。仓库全名、commit SHA、node ID、gist ID、 API 路径模板——全部命中。

今天这条规则的杀伤半径有限，因为 GSM 不抓 body。但一旦按 #428 落地 `netTap`：

```text
MAX_BODY_PREVIEW_BYTES = 256 * 1024      每个响应体预览上限
BODY_CAPTURE_BUDGET_PER_MINUTE = 60      每分钟最多 60 次 body 读取
```

且 `netTap.js` 明确"**JSON 先行解析为对象再做脱敏**"，目的是让 JSON 内部嵌入的凭据也被处理。于是 GitHub API 响应里每一个 ≥20 字符的 `full_name` 都会被 `***` 化——导出 bundle 里既留下了 256KB 的 body 内容（隐私问题），又丢失了所有仓库标识（可用性问题）。**两个方向的坏处同时发生。**

这正是报告 §9.3 想表达的张力（"没有 token ≠ 没有隐私"）的另一半：**单靠"全量抹除可疑字符串"换取安全，会把诊断信息一起抹掉。** 报告只讨论了"上游不够严"，没有讨论"上游同时也是太粗暴，而 GSM 已经继承了这条规则"。

**建议：** GSM 应改为"允许名单"式处理——对已知安全标识符形态（GitHub `owner/repo`、40 位 hex SHA、相对路径）显式免脱敏，而不是依赖通用正则的宽字符集。这条必须写进 §9.6 的 sanitization vectors，否则 bundle 无法用于实际排障。

### 1.5 反向纠偏：报告高估了三处本地秘密的暴露风险

为避免过度纠正，此处明确记录一处**报告焦虑过度**的地方：

报告 §9.3 A 类列出了 proxy password、RPC secret、backend API secret。实测这三个 GSM 持久化秘密**已经被上游 `redact.js` 的结构化规则完整覆盖**：

- `sanitizeObject` 检查字段名是否在 `SENSITIVE_FIELD_NAMES`（含 `password`、`secret`、`token`、`backendApiSecret`）；
- 且额外做了子串兜底：`lowerKey.includes('password' | 'secret' | 'token' | 'apikey')` 一律 mask。

GSM 持久化的 `proxyConfig.password`、`rpcDownloadConfig.secret`、`backendApiSecret` 全部落在上述规则内。**这三个不需要额外补规则**，报告把它们列出来是对的，但不必当作"上游覆盖不到"的缺口来处理。真正的缺口只有 §1.3 列出的那四类。

## 2. 本轮复核中**确认正确**的报告判断

不应因为发现了问题就全盘重估。以下条目经源码比对，报告描述与实际实现一致：

| 报告断言 | 实测结果 |
| --- | --- |
| §5.1-8 大分片 idle 写入最小 60 秒冷却 | `largeShardIdleWriteMinIntervalMs = 60_000` ✓ |
| §5.1-8 flush 立即写、绕过冷却 | 注释与实现均绕过 ✓ |
| §5.1-9 小 shard 不被大 shard 拖延 | 节流按 `Map<ShardName, number>` 逐 shard 记账 ✓ |
| §5.1-6 读取失败与"键不存在"严格区分 | `hydratedIncomplete` + `foundButUnreadable` ✓ |
| §5.1-5 meta 缺失可打捞 orphan shards | `salvageOrphanedShards()` 实存 ✓ |
| §5.7 上游 `WORKSPACE_REFERENCE_FIELDS` / `VALUE_FIELDS` 清单 | 完全一致，共 11 + 7 项 ✓ |
| §5.9 `PERSISTENCE_SHARD_FORMAT` 独立于 Store version | 确为独立常量 `= 1` ✓ |
| §6.2 禁止裸 fetch + npm ProxyAgent 混用（补充段） | 本机已确认存在该混用模式，成立 ✓ |

**补一条报告没写但会影响测试设计的实现细节：** 冷却是否生效取决于 `SHARD_SIZE_WARN_BYTES = 5 * 1024 * 1024`——只有上次成功写入体积 **超过 5MB** 的 shard 才会进入 60 秒节流（源码第 526 行 `if ((lastWrittenShardBytes.get(shard) ?? 0) <= SHARD_SIZE_WARN_BYTES) return 0;`）。因此 §5.10 的用例 13/14（pagehide 绕过节流、core 不被大 shard 拖延）必须用超过 5MB 的数据构造，否则测试会因为阈值没达到而看似通过却什么都没验证。

## 3. 落到执行清单上的变更

**Phase 0.5（去风险包）追加：**

1. 以 GSM `logSanitizer.ts` 为唯一真源，把四条 GSM 独有规则（细粒度 PAT、多 token 前缀、键值对形态、PEM 块）整理成可移植单元，作为后续主进程脱敏的基础；**不接受**上游 `redact.js` 反向导入。
2. 扩展上游既有的 `tests/fixtures/sanitization-vectors.json`（该夹具已存在，且同时驱动 vitest 与 node:test 三处测试），而不是另起一套 GSM vectors。注意该夹具头部 `$comment` 明确要求：**不得加入在各副本间行为本就不同的向量**——GSM 若新增差异域，需单独 fixture，不要塞进共享清单制造假的一致性。
3. 度量范围从"`classificationNavigation` 是否该移出 core"扩大为**全部持久化字段的 byte size**，重点覆盖 `readReleases` / `releaseSubscriptions` / `readForks` / `classificationSchemes` / `accountWorkspaces`。

**Phase 1 门禁追加：**

4. 全局 shard 字段唯一性断言（覆盖全部 partialize 输出字段，而非仅 AccountWorkspace 字段）；实现时先从 `core` **移除**再向 `organization` 添加那 4 个冲突字段。
5. 涉及节流的测试用例必须先构造 > 5MB 的分片。

**Phase 6 约束追加：**

6. 若保留 `netTap` 的 body capture，`MAX_BODY_PREVIEW_BYTES = 256KB` 与每分钟 60 次的预算应与报告 §9.3 的 B 类策略对齐——即默认关闭 body，debug 才开；并对 §1.4 的标识符误伤补 allowlist。
