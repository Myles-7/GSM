## 0. 复核结论

**原报告的事实基础完全可靠，可以作为迁移实施依据。** 本次抽取的 12 项可验证断言（tag SHA、上游漂移幅度、增量规模、共同祖先、本地偏离量、脏文件构成、dirty 重叠清单、Store 版本、依赖版本、缺失模块、缺失 IDB 原语、既有账本结构）**全部与实测一致，没有一处失真**。这在同体量的迁移审计文档里很少见。

但它在**可执行性**上有 7 处开口，需要在开工前补齐。核心缺口是：

1. 一个**本机现存缺陷**（`undici` 混用）未被识别，且与 #426 直接耦合；
2. **没有任何可用的 before 基线**，导致第 18.6 节的 before/after 门禁在开工当天无法成立；
3. **118 个未跟踪文件未三分**，Phase 0 的"冻结"缺一个可操作步骤序列；
4. 建议的 Phase 6（诊断）顺序会让风险最高的 Phase 1/2 **在最弱观测手段下施工**；
5. 建议新建的迁移账本与既有 `upstream-base.json` / `P0.2.0-migration-ledger.md` 惯例**冲突**，正确的落点应为升级 schema 而非新增 md。

## 2. 报告真正有价值的三个判断

**① 把"文件冲突"升级为"语义冲突"。** 这是全文最重要的方法论。`src/store/normalizers/persistedState.ts`、`accountWorkspace.ts`、`electron/main.js` 即使文本合并无冲突，也可能因为上游不认识 `classificationSchemes` / `classificationNavigation` / `subcategories` / `repositoryOrder` 而静默丢数据。第 2.3 节列出的 14 条**已提交但语义相交**路径，比 Git conflict 更有决策价值。

## 3. 七处缺口与补强建议

### 3.1（最高优先级）本机已存在 `undici` 混用模式，报告未识别

报告第 6.2 节把 `outboundFetchGate` 当作**未来引入 #426 时才需要**的护栏。实测发现该风险模式**今天已经存在**：

```text
electron/main.js:415-423   const dispatcher = getFetchDispatcher();  // 来自 require('undici').ProxyAgent
                           await fetch(url, { ..., ...(dispatcher ? { dispatcher } : {}) });  // 全局裸 fetch
electron/main.js:507-512   同上（X GraphQL 鉴权路径）
```

`getFetchDispatcher()`（main.js:378-407）返回的是 **npm 用户态 `undici` 的 `ProxyAgent` 实例**，却被传给 **Electron/Node 内置的全局 `fetch()`**。这正是上游 `outboundFetchGate.test.js` 要防的 `UND_ERR_INVALID_ARG` 触发条件。

对照正常写法——WebDAV 通道是正确的同源配对：

```text
electron/main.js:1036  fetchImpl: (...args) => require('undici').fetch(...args),
electron/main.js:1037  getDispatcher: getFetchDispatcher,   // 同源 dispatcher
```

**结论与建议：**

- 这是一个**独立于迁移的现存脆弱点**，当前 `undici@7.29.1` 是否实际报错取决于 Node/undici 内部的 Dispatcher 校验强度，不宜断言"现在必炸"；但该模式属于已知高危写法。
- 一旦按 #426 把 `undici` 升到 8.x，**该写法成为直接触发路径**。因此修它应是 **Phase 2 的前置动作**，而不是等迁移时顺带重构。
- 修法很小：把 main.js 中带 dispatcher 的调用统一改为 `require('undici').fetch(url, { ...opts, dispatcher })`。
- 应针对该模式补一个本机 test，等价于上游 `outboundFetchGate.test.js` 的语义：**禁止裸 fetch + npm ProxyAgent 同现**。

### 3.2 没有 before 基线，第 18.6 节门禁无法成立

第 18.6 节要求"保留 before/after 基线、不允许用'仓库本来就有失败'掩盖新增失败"。但 audit 当下**没有记录任何基线**：118 个未跟踪文件的存在意味着即使 `npm run test:run` 的结果也未被锚定。

建议将其提升为**不可跳过的前置动作**：

```text
npm run build              → 记录通过/失败与错误清单
npm run test:run           → 记录失败用例全名单
npm run test:electron:plugins / test:electron:webdav → 同上
npm run lint               → 记录既有 error/warning 计数
```

`P0.2.0-migration-ledger.md` 的先例（"全仓库仍有 47 errors / 11 warnings，不声称全绿"）证明这个基线是后续诚实归因的唯一凭据。**没有它，Phase 1 出问题时无法判断是回归还是历史债。**

### 3.3 118 个未跟踪文件需要三分，而不是整体冻结

第 2.1 节要求"明确哪些 dirty 是正式功能、哪些是临时研究产物"，但没有给出分类口径。建议按三分类落清单：

- **A 类**：正式功能源码/文档 → 进 checkpoint commit；
- **B 类**：验证产物、临时日志、fixture → 不入库，单独目录归档或记录路径；
- **C 类**：误生成的构建/缓存 → 加入 `.gitignore` 或直接删除。

这一步不做，后续每个阶段的"我改了什么"都无法与现有未跟踪内容区分。

### 3.4 Phase 0 缺少可执行动作序列

"冻结与恢复点"目前只有目标，没有步骤。考虑到 266 项 dirty **无法通过 git worktree 直接携带**，建议固化为：

```text
1. git add -A（先不要 commit）
2. git commit -m "wip(local-agent-organization): pre-v0.8.6-migration checkpoint"
   —— WIP 提交不是发布物，目的是让工作区可 fork
3. git tag recovery/pre-v0.8.6      # 沿用 P0.2.0 的 recovery/<stage> 命名
4. 保存 untracked 三分清单（§3.3）
5. 采集 before 基线（§3.2）
6. git worktree add ../gsm-upgrade-v086 6b30a96   # 或新建 upgrade 分支
```

命名应对齐 P0.2.0 既有惯例（`recovery/pre-P0.2.0`、`personal-P0.2.x` tag）。

### 3.5 Phase 6（诊断）应局部前置

第 15 节把诊断放在 Marketplace 与 Insights 之后，理由是"避免同时排查功能 bug + 日志 bug"。这个理由在**接线层**成立，但对**纯函数层**不成立：

- `electron/redact.js`、`redact.test.js`、`electron/systemInfo.js` 是**零接线依赖的独立纯模块**，落地不触碰 `main.js`；
- Phase 1（分片持久化）和 Phase 2（多网络栈）恰恰是**最难观测、最容易静默出错**的两个阶段，而当前它们只能在弱观测下施工。

**建议：** 抽取 `redact.js` + vectors 测试作为 **Phase 0.5 去风险项**先落地（独立于 v0.8.6 移植亦可），把完整诊断 wiring（netTap / fetchCapture / main journal / UI）仍留在 Phase 6。这样能在不引入交叉风险的前提下，给 Phase 1/2 提供最小可用的脱敏日志能力；同时第 9.3 节的 A/B/C 三档隐私分级也应在此时确定，而不是等到最后。

### 3.6 `organization` shard 的边界未度量，需转为 Phase 0 动作

第 5.4 节建议新增 `organization` shard 是对的，但对 `classificationNavigation` 是否留在 `core` 的判断被悬置（"不要凭名称决定，先用真实备份统计 JSON byte size"）。

该判断会直接决定 shard 切分代码，属于**实施前必须关闭**的决策。建议在 Phase 0 用一次真实数据导出得出各字段 byte size 分布，然后固定 shard 表；否则存在"Phase 1 中期才改 shard 边界"的返工风险。

### 3.7 账本落点：应升级 `upstream-base.json` 至 schemaVersion 3，而非新建 md

第 22/23 节建议把 consumed upstream range 记入 `docs/personal/upstream-base.json` 或"新建 `v0.8.6-migration-ledger.md`"。实测该文件已存在（schemaVersion 2），但**结构无法承载报告的诉求**：

- 现有字段只有单一 `upstreamVersion: "0.8.4"` 与 `upstreamMergeCommit`（最后一次完整 merge），**没有 per-PR 的 absorbed / adapted / conditional / skipped 记录位**；
- 既有命名惯例是 **`P0.2.x-*.md`**（个人发布版本号），而不是 `v0.8.6-*.md`（上游 tag）；新建 `v0.8.6-migration-ledger.md` 会打破 `P0.2.0-migration-ledger.md` 已建立的对偶惯例。

建议：

- 扩展 `upstream-base.json` 到 **schemaVersion 3**，新增 `consumedUpstreamRange`（per-PR 状态枚举 + 验收 commit）与 `intentionalDeviations`；
- 迁移 ledger 沿用 `P0.2.2-migration-ledger.md`（或下一个个人版本号），与 `P0.2.0-migration-ledger.md` 同构；
- 沿用 P0.2.0 已验证的两个收尾小节：**「数据与阶段恢复」**与**「禁止顺带引入」**。后者尤其应在本轮显式写出：`不引入 #436`、`不顺带重编号 Store version`、`不顺带重写 AGY/HTML Reading/MCP 接线`、`不顺带清 lint 历史债`。
