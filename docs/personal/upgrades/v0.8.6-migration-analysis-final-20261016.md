## 1. 最终结论：五个工程阶段完成，不按 PR 顺序搬文件

当前 GSM 不是 v0.8.5 的轻量 fork，而是：

```text
upstream v0.8.4 完整基线
  + 第一批个人定制
  + v0.8.5 选择性迁移
  + 双分类 / AI Organization / HTML Reading / AGY / MCP / Home Sync 等后续开发
  + 本轮 adapted(v0.8.6)
```

因此本轮必须采用 **selective forward-port**。迁移单位是“行为、数据不变量、安全约束和测试”，不是上游文件。

推荐只保留五个实施阶段：

| 阶段 | 目标 | 上游范围 | 同步修复当前 GSM |
| --- | --- | --- | --- |
| **1. 数据完整性、恢复与持久化** | 先把数据安全边界做稳，再换分片存储 | #424 + #434 persistence | DB migration 断层、workspace 判空、identity remap、HTML Reading identity、WebDAV 恢复分叉、classification 引用完整性 |

## 3. 当前 GSM 深度盘查：本轮必须一起治理的问题

这些不是“可选清理”。其中 P0 项若不在对应阶段处理，会直接削弱迁移正确性。

### 3.1 P0：后端 schema migration 已出现真实断层

当前：

- `server/src/db/migrations.ts` 的最高版本仍是 **v4**。
- 新字段通过 `initializeSchema()` 中的 `addColumnIfMissing()` 添加，包括 `repositories.classifications`、`category_id`、`subcategory_id`、`category_candidates`、`category_legacy`、`ai_details` 等。
- 正常 server 启动只调用 `runMigrations()`。
- 已经是 `schema_version=4` 的旧数据库会在 `currentVersion >= targetVersion` 时直接 return，因此不会再次调用 `initializeSchema()`。

后果：真实旧 v4 数据库可能缺少新列，而新 routes 已经读写这些列。

同时 `server/src/index.ts` 目前只在 `version < 3` 时做 migration backup；如果新增 v5，**v4 → v5 默认也不会备份**。

Stage 1 必须：

1. 新增明确的下一版 migration（当前应为 v5），把所有“上线后新增但没有 migration version”的列和必要结构纳入。
2. migration 前备份条件改成“存在旧 schema 且版本低于当前 target”，不要继续写死 `< 3`。
3. fixture 必须模拟“真实旧 v4、已有行、缺新列”，不是 fresh DB。
4. 验证升级后列完整、旧行保留、重复启动幂等、备份文件确实产生。

### 3.2 P0：账号 workspace 的非空语义已经过时

`workspaceHasData()` 目前没有计入：

```text
classificationSchemes
classificationNavigation
externalDiscoveryChannels
subcategories
subcategoryOrder
repositoryOrder
```

一个账号如果只拥有 technology taxonomy、子分类、人工顺序或外部发现源，可能被视为空 workspace。登录时 backend restore / parked workspace 选择就可能绕过冲突保护。

Stage 1 必须：

- 把这些字段纳入统一 non-empty helper。
- Login restore 冲突检测、account switch、parked snapshot 共用同一语义，不要再复制条件。
- parked `classificationSchemes` / navigation 进入 live state 前做真实 schema normalization，不只 type cast。
- 测试 classification-only / subcategory-only / external-feed-only workspace。

### 3.3 P0：repository identity migration 没有覆盖当前双分类和 v3 Organization 全结构

当前 identity rekey 已覆盖不少 legacy 字段，但仍有可执行引用遗漏。

至少需要重新审计并覆盖：

- root `repositoryOrder`
- `classificationSchemes.purpose/technology.repositoryOrder`
- parked `accountWorkspaces` 内两套 scheme / order
- AI Organization v3 `dual.understanding`
- `dual.summaries`
- mutable `errors` / `verificationIds`
- 两套 scheme `entries`
- `structureOperations` 中仍参与 restore/apply 的 members / entriesBefore
- `application.repositoryIds` / `membersAfter`
- server/Home canonical proposal 中对应 mutable references

原则：

- **仍参与 apply / restore / conflict / coverage 判断的 repo id 必须重映射。**
- 纯历史审计证据可按既有策略保留旧 ID，但要显式区分 historical 和 mutable，不允许靠状态字符串零散判断。
- 建议实现一份“identity reference policy + remap helper”，客户端、server、Home 共用测试向量。

### 3.4 P0：HTML Reading 完全没有进入 repository identity participant

HTML Reading 是独立 IndexedDB（`gsm-html-reading`），内部大量结构以 repo id 为 key 或字段：

- states / names
- positions / resume
- snapshots / section entries
- projectSources / candidateSources
- star batches / return operations

如果主 Store 完成 oldId → newId，但 Reading 未迁，note/read/candidate/继续阅读位置会变成孤儿数据。

Stage 1 必须：

- 将 HTML Reading 注册为 account-bound identity participant。
- 提供 backup → remap → verify → rollback/restore。
- 接入 repository identity maintenance writer gate，migration 时拒绝并发 Reading 写。
- cache 类数据可以明确选择“重映射”或“失效重建”，但必须写进策略和测试。
- 其他账号数据不能被当前账号 rekey 修改。

### 3.5 P0：后端 technology membership 只有 shape 校验，没有 effective referential validation

frontend `incomingOrganizationSnapshot()` 会验证 technology membership 的 category/subcategory 是否真实存在于 technology scheme；server repository routes / sync v2 主要只做 schema shape 校验。

因此 server 可以保存：

```text
结构合法
但 categoryId / subcategoryId 指向不存在 taxonomy 节点
```

Stage 1 必须：

- 对 server canonical classification 增加 effective final-state 引用校验。
- sync v2 按同一批次的最终 repo + organization 状态校验，不能因 record 应用顺序导致“本来合法的同批更新”误拒绝。
- 非法 batch 全体回滚，不落半份 canonical state。
- 旧客户端只更新 metadata 时继续保留已升级的 technology 数据。

### 3.6 P0：WebDAV restore 仍绕开了已有的安全恢复引擎

当前本地文件恢复已经具备：

- schema decode / identity 检查
- restore preview / merge / replace plan
- `LocalRestoreJournal`
- before/after hash
- Home staging
- repository identity writer gate
- durable persistence verify
- 崩溃后 continue / undo

但 `useBackupActions.ts` 的 WebDAV restore 仍然是：

```text
JSON.parse
→ discovery import
→ setState organization
→ release/read state
→ AI/WebDAV/proxy/RPC/config
→ 各段 try/catch
```

中途失败可以留下部分恢复，而且当前测试的成功路径甚至因为 mock 缺 `setRouteMode` 会打印 TypeError 后仍判通过。

Stage 1 处理原则：

1. **不要发明第三套恢复协议。** WebDAV 下载后先走统一 backup schema/identity/preflight。
2. repositories / organization / UI 等无敏感业务数据复用现有 plan + journal 核心。
3. WebDAV/AI/proxy/RPC secret 不得写入明文 `LocalRestoreJournal`；敏感配置使用独立 preflight + commit lane，失败要有同会话补偿恢复，并明确 partial 状态。
4. discovery workspace 在写 Store 前先完成完整校验；若无法与 Store 做同事务，保存 pre-image/receipt，并在后续失败时补偿恢复。
5. 新 cloud backup 写入 account identity；旧无 identity 备份必须显式 legacy confirmation。
6. 修复 `useBackupActions.test.tsx` fixture，使“成功恢复”不再靠 catch warning 通过。

### 3.7 P0：#424 分片会直接影响现有安全恢复 durability verification

当前 `localBackupRestore.ts` 在 `flushAppStorePersistence()` 后直接：

```text
indexedDBStorage.getItem(appPersistenceOptions.name)
→ JSON.parse(...).state
→ hash verify
```

#424 迁成 shards 后，base key 不再代表完整 Store，这段验证会失效。

Stage 1 必须同时改成：

- persistence 层提供唯一的 `readPersistedSnapshot()` / strict full-snapshot API。
- safe restore、测试工具、必要的 recovery 验证都通过该 API，不直接知道 shard key。
- `gsm-local-backup-journal:<account>`、`gsm-identity-journal:<account>` 等独立 journal key 不能被 Store shard cleanup / clear-derived-keys 误删。

### 3.8 P0：Electron 现在已经存在 npm ProxyAgent + global fetch 混用

`getFetchDispatcher()` 返回 npm `undici.ProxyAgent`，但 X timeline 和 X GraphQL 路径把它传给全局 `fetch()`；WebDAV 则使用 npm `undici.fetch()`。

这与上游 `outboundFetchGate` 防的风险同构。当前 `undici=7.29.1`；升级到 8.x 前必须先统一 fetch family。

Stage 2 必须：

- 所有使用 npm dispatcher 的请求统一走 npm `undici.fetch` / `mainFetch`。
- 统一 ProxyAgent 生命周期，避免 X 路径创建后不 destroy。
- 加静态/运行时 gate，禁止再次出现 global fetch + npm dispatcher。

### 3.9 P0：Plugin manifest / registry network 权限模型不一致

当前：

- `manifestSchema.js` 接受 `network:<domain>`。
- manifest test 已使用 `network:api.github.com`。
- runtime `pluginRegistrySchema.js` 仍硬编码 `network:fetch`。
- registry JSON schema / CI 与 runtime validator 也不是同一套实现。

Marketplace 上线后这会变成真实安装兼容和权限提示问题。

Stage 3 必须：

- canonical 权限统一为 `network:<hostname>`。
- manifest / runtime registry / JSON schema / CI checker / permission prompt 使用同一 parser 或共享测试向量。
- registry `networkTargets` 与 `network:*` permissions 必须一一一致、去重。
- 如需要读取历史 `network:fetch`，只做 legacy read compatibility，不作为新 canonical permission。

### 3.10 P0：Plugin `suggestedAction: save` 可绕过 downloads permission

`pluginProtocol` 允许：

```text
{ type: 'text', suggestedAction: 'save' }
```

但 `pluginManager.runAction()` 只检查 `external:open` 和 `clipboard:write`；renderer 会直接用 `<a download>` 保存。

Marketplace 扩大第三方插件来源前必须修：

- `save` 至少要求 `downloads:create`。
- 更推荐走现有 host-mediated `downloads.saveFile`，把文件名/size/取消/系统 dialog 继续放在宿主能力边界。
- 增加无权限插件请求 save 必须被 main-process 拒绝的测试。

### 3.11 P1：诊断系统既缺覆盖，也存在 sanitizer 可用性问题

当前 renderer/backend 已有日志，但 v0.8.6 的 main/network/plugin diagnostics 尚未落地。

GSM 当前 sanitizer 比 upstream `electron/redact.js` 更强，已经覆盖：

- `github_pat_...`
- `gho_/ghu_/ghs_/ghr_...`
- `password=...` / `api_key: ...`
- PEM private key
- MCP bearer token

这些能力不能回退。

同时当前通用规则：

```ts
/^[a-zA-Z0-9+/=_-]{20,}$/
```

会把部分合法 owner/repo、SHA、路径标识当 secret。#428 一旦加入 JSON body capture，会大幅降低诊断 bundle 可用性。

Stage 2 必须：

- 以 GSM sanitizer 为 source of truth，主进程/renderer/server/plugin 共享向量。
- 为明确安全的 repo full name、commit SHA、有限 API path 等建立 shape-aware 例外，不靠简单“长字符串全抹”。
- 导出 bundle 时再次 deep redact，不能假设写入时已经安全。
- 默认 metadata-only；debug body 也要硬拒绝 AI prompt/response、X Cookie、WebDAV body、SMTP、AGY/MCP、本地项目内容、私有 repository body 等高敏类别。

### 3.12 P1：trusted IPC 目前缺 one-way `.on` 安全包装

当前 `createTrustedIpcMain` 主要包装 `.handle`；上游 diagnostics shutdown/flush 有 one-way IPC 使用场景。

Stage 2 不允许直接在 `main.js` 新增裸 `ipcMain.on`：

- 给 trusted registrar 增加受信 `.on`/必要的 cleanup 语义。
- 测试 untrusted sender/frame 发 one-way event 时没有副作用。
- 继续保留“main 注册 privileged channel 不得绕过 shared trusted boundary”的静态门禁。

## 4. 不能回退的现有 GSM 契约

下面这些是本地比上游更强或更完整的能力，迁移代码必须围绕它们适配。

### 4.1 Store / classification

- Zustand Store persistence version = **17**。
- purpose 是 legacy/GitHub Lists canonical projection；technology 独立 taxonomy。
- `classificationSchemes`、navigation、subcategories、人工 order 都是正式数据。
- accountWorkspaces 按 GitHub numeric id 隔离。
- AI Organization v3 有 scope、evidence、manual lock、revision/checkpoint、apply/restore/CAS。

### 4.2 Local backup / Home

- safe restore 有 durable journal 和 continue/undo。
- Home operations 先 stage，再与 App durable write 协同。
- repository identity migration 有 maintenance writer gate 和恢复 journal。
- 代码回滚不能代替 Store/Home/SQLite/Reading 数据恢复。

### 4.3 HTML Reading

- 独立 IndexedDB `gsm-html-reading`，当前 DB v5。
- migration backup、fingerprint/receipt 防 replay、transaction deadline。
- Gmail credential 使用 Electron safeStorage。
- SMTP 结果未知时标记 unconfirmed，**绝不自动重发**。

### 4.4 MCP / Local Agent

- loopback-only + bearer / `x-mcp-token`。
- Streamable HTTP + legacy SSE compatibility。
- organization broker 绑定 trusted renderer/sender、pending limit 和 deadline。
- external agent 只能修改 draft，不能越权 apply/unlock/manual。

### 4.5 Electron

- `nodeIntegration=false`
- `contextIsolation=true`
- `sandbox=true`
- `webSecurity=true`
- privileged IPC 绑定 trusted main frame/document。

### 4.6 WebDAV

`electron/webdavIpc.js` 已有：

- trusted main frame
- request ownership + requestId
- explicit cancel
- per-renderer max 8 concurrent
- request/response max 64 MiB
- header budget 16 KiB
- `redirect: error`
- response header allowlist
- credential-safe fixed failure

这些必须保留。尤其 mutation 请求一旦开始而结果未知，**不得自动 replay**。

### 4.7 Plugin V1.4

- main-process `pageSessions`
- sessionToken + requestId
- completed replay rejection
- max 8 pending
- 120 requests/minute
- disable/uninstall/navigation/account switch revoke
- late result rejection
- binary/base64/fileName/args budget validation

#433 的 `network.request` 必须加入这套模型，不能替换这套模型。

## 6. Stage 1 — 数据完整性、恢复与分片持久化

### 6.1 进入 Stage 1 前先冻结当前输入

这仍属于 Stage 1，不新建 Phase 0。

1. 将当前 122 个 untracked 分为：正式源码/文档、验证产物、缓存/误生成物。
2. 保存 checkpoint commit 和 `recovery/pre-v0.8.6-*` 恢复标签。

4. 保存 before baseline：
   - `npm run typecheck`
   - `npm run build`
   - `npm run test:run`
   - `npm run lint`
   - `cd server && npm test && npm run build`
5. 记录历史失败，不把它们算成迁移新增回归。

本轮审计已做的 targeted baseline 只作为定位依据，不替代上述正式 baseline：

### 6.2 先修 server schema / canonical integrity

### 6.8 IndexedDB backend 必须与 shards 成套迁

需要的语义：

- multi-get / multi-set / delete-many 在一个 IDB transaction 中提交。
- strict read 区分 missing 与 unreadable。
- fallback authority marker，避免 localStorage / IDB 双权威。
- meta 缺失时可 salvage orphan shards。
- legacy single-key 成功转移后才退役。
- clear 时删除 base + derived shard/meta key，不误删 identity/backup journals。
- pagehide/beforeunload flush 绕过 large-shard cooldown。

不要保留当前“对已启动 IDB promise 做短 timeout，超时后 localStorage fallback，但原 IDB transaction 可能迟到提交”的双权威竞态。

## 13. 每阶段停止条件与恢复策略

### Stage 1

停止条件：任何 Store/server/Home/Reading 数据不一致、旧 profile 无法读、restore/rekey journal 无法恢复。

恢复不能只 revert code；使用 checkpoint + Store/Home/SQLite/Reading 一致备份共同恢复。

### Stage 2

停止条件：trusted IPC 回退、X/WebDAV proxy 行为异常、mutation 被 replay、diagnostic bundle 泄密。

Stage 2 不应改变用户业务数据 schema，可代码回滚，但日志/插件安装目录需按本阶段 backup 恢复。

### Stage 3

停止条件：permission escalation 静默启用、token 进入 plugin/IPC/log、session revoke 失效、Marketplace replace 失败丢旧插件。

恢复插件代码目录时保留 plugin data/log，除非用户明确要求清理。

### Stage 4

停止条件：官方插件依赖宿主越权能力、Repo Insights resize crash、Info Card export 错画幅、Markdown/README regressions。

### Stage 5

停止条件：出现无法解释的新 test/build/type/lint 回归、真实 profile 与 before baseline 数据不一致、依赖 audit 出现本轮新增高风险问题。

## 14. Codex 执行时的固定工作方法

每个阶段都遵循：

1. 先读当前 GSM 实现和 callers。
2. 再读 PR first-parent diff 和 `v0.8.6:<path>` final blob。
3. 写出本阶段要保留的 GSM invariants。
4. 先补能暴露当前缺陷的测试，再改实现；对纯性能重构可先固定 benchmark/baseline。
5. 函数/模块级迁移上游行为。
6. 跑本阶段 targeted gates。
7. 查看 `git diff`，确认未覆盖不相关 dirty work。
8. 保存本阶段 commit + test evidence。
9. 只有本阶段停止条件全部关闭才进入下一阶段。

不允许因为“cherry-pick 能自动成功”就认为语义正确。

### Plugins
