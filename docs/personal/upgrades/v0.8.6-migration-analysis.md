## 0. 结论先行

这次升级**不适合对当前 GSM 直接执行 `git merge upstream/main`、`git merge v0.8.6` 或批量 cherry-pick merge commit**。当前项目已经不是轻量 fork，而是经历了“v0.8.4 上大量个人开发 → 选择性吸收 v0.8.5 → 在吸收后的架构上继续大量个人开发”的二次分叉。现在的 HEAD 同时包含：v0.8.4 以来的个人能力、v0.8.5 的选择性上游语义、以及 v0.8.5 迁移后新增的双分类、AI Organization、账号工作区、HTML Reading、AGY、本地 Agent、Home/Sync、插件 V1.4 会话安全、诊断与恢复等产品契约；与此同时，v0.8.6 又集中修改了持久化、Electron 主进程网络、插件管理与页面桥、日志、WebDAV、Markdown、README 弹窗和 package/lock。文本自动合并即使能成功，也不能证明数据契约和安全语义正确。

推荐的总策略是：**冻结当前个人开发状态 → 固定 v0.8.6 tag → 按能力域 selective forward-port → 每个阶段吸收上游“行为、不变量、测试和修复链” → 在 GSM 当前架构上重新接线 → 最后再登记已消费的上游范围。**

本次最值得吸收的四组能力是：

1. **#424 + #434 分片持久化**。这是性能收益最大的一项，也是风险最高的一项。GSM 当前仍会把整份 Zustand 持久状态 `JSON.stringify` 后写到单一 IndexedDB 键；上游把大状态拆成原子分片，并用引用判脏只重写变化分片。该设计应该吸收，但必须为 GSM 的 `classificationSchemes`、双分类导航、子分类与仓库人工顺序重新设计 shard，不可直接复制上游 `shards.ts`。
2. **#427 + #433 + #434 插件能力升级**。Marketplace、自定义 GitHub 插件源、V1.5 `network.request` 与 Repo Insights 都有明显产品价值。GSM 当前 V1.4 页面会话安全反而比 #433 的原始基础更强，所以应把上游能力嵌入现有 session token、请求去重/限流、停用撤销、账号切换失效和 AI 任务日志模型，而不是替换现有 `PluginPageViewer/pluginManager`。
3. **#426 + #434 WebDAV/主进程网络修复**。真实底层连接错误、Node→Chromium 回退、手动安全重定向、PROPFIND 检测值得吸收。GSM 已经有桌面请求取消和“未知结果的 PUT 不自动重放”语义，这一安全契约必须保留。
4. **#428 + #434 全链路诊断**。主进程、渲染端、后端、插件和网络请求统一诊断非常有价值，但 GSM 比上游多出 AGY、MCP、HTML Reading、SMTP、本地 Agent、RPC 密钥等敏感面，不能原样开启“调试模式抓 body”。需要把上游日志引擎与 GSM 的隐私边界合并。

低风险、可以较早吸收的更新是 #429 Repository Chat 代码块修复和 #431 README 近全屏；#432 + #435 Repo Info Card 主要位于示例插件，可在宿主协议稳定后重构；#423/#430 依赖更新不能照抄 lockfile，必须基于 GSM 当前真实依赖树重算。

### 0.2 明确不建议的做法

- 不跟随 `upstream/main` 开发。本次目标是 `v0.8.6`；`upstream/main` 已经包含 v0.8.6 之后的 PR #436。
- 不在当前数百项 dirty/untracked 状态上直接做上游 merge。具体数量会随着个人开发变化，迁移开始时必须重新采集一次基线。
- 不用 `git checkout --theirs` 覆盖 `electron/main.js`、`preload.js`、Store、WebDAV、插件系统、locale 或 package files。
- 不把 #434 当成“迁完全部功能以后再 cherry-pick 的最后一个修复”。它必须被拆开并入各自阶段。
- 不因为上游 `PERSISTENCE_SHARD_FORMAT=1` 就把 GSM 新字段自动落进 `core`；那会重新制造大 core 序列化问题，并可能漏掉账号工作区判脏。
- 不直接采用上游 `network.request` 后让所有第三方插件持用户 GitHub Token 对任意 `api.github.com` 白名单路径获取私有仓库数据，必须明确权限语义与私有数据策略。
- 不用 #423/#430 的 `package-lock.json` 覆盖当前 lock。

### 0.3 这次迁移真正要处理的是“五层历史”，不是“8.5 → 8.6”一层 diff

建议以后所有迁移判断都使用下面的历史模型，而不是把当前 HEAD 当成“接近 v0.8.5 的 fork”：

```text
U84  = upstream v0.8.4 完整共同基线
L1   = 你在 8.4 上形成的第一批个人定制
U85s = 从 v0.8.5 选择性吸收的能力/修复（不是完整 merge）
L2   = 迁移 8.5 后继续形成的第二批个人定制
U86s = 本次准备从 v0.8.6 继续选择性吸收的能力/修复

当前 GSM = U84 + L1 + U85s + L2
目标 GSM = U84 + L1 + U85s + L2 + U86s（经过本地语义适配）
```

这会带来 6 类冲突，Codex 不能只处理 Git 标红的那一种：

| 冲突类型 | 典型表现 | 本次处理原则 |
| --- | --- | --- |
| 文本冲突 | 同一行/函数被上下游同时修改 | 函数级重写，不用整文件 ours/theirs |
| 语义冲突 | Git 能自动合并，但上游不知道 GSM 新字段/安全规则 | **以 GSM 现有契约为主，吸收上游行为而非文件** |
| 历史冲突 | v0.8.5 已选择性迁过一部分，v0.8.6 又改同一区域 | 先确认 v0.8.5 当时到底吸收了什么，再读 v0.8.6 final blob |
| 数据冲突 | Store、workspace、IDB 格式、backup/restore 的结构变化 | 任何 schema/shard 变化都必须有旧数据往返测试和 downgrade 预案 |
| 安全冲突 | 插件 token、WebDAV replay、日志正文、IPC/page session | **本地更严格的安全不变量不因上游功能升级而回退** |
| 依赖冲突 | package/lock 已被本地功能多次改动 | 只迁 manifest 意图，基于当前树重算 lock 与 audit |

因此每个 v0.8.6 功能都要回答四个问题：

1. 它修改的是“上游仍拥有主导权”的区域，还是已经被 GSM 重新定义的区域？
2. v0.8.5 是否已经迁过它的前置能力，且当时是否做了本地改造？
3. v0.8.6 的实现是否会覆盖 L1/L2 的数据、安全、账号隔离或恢复语义？
4. 如果不采用上游实现，是否仍需要吸收其测试、错误处理、稳定性修复或安全约束？

**这四问比“这个文件有没有 conflict”更重要。**

## 3. GSM 当前必须保护的产品与数据契约

迁移时，下列能力应当作为“新主干架构”而不是旧 fork patch 来对待。

### 3.1 Store v17 与双分类 / Repository Organization

当前 `src/store/persistence/options.ts` persistence version 是 17。持久状态已经包含上游 v0.8.6 不知道的新字段：

- `classificationSchemes`
- `activeClassificationScheme`
- `classificationNavigation`
- `subcategories`
- `subcategoryOrder`
- `repositoryOrder`
- 以及原有 `customCategories`、`categoryOrder`、`hiddenDefaultCategoryIds`、`defaultCategoryOverrides` 等。

`normalizePersistedState()` 还会：

- 恢复/修正 Repository Organization；
- 恢复双分类方案；
- 从 auth mirror 回填 GitHub token/backend secret；
- 清除退休翻译设置；
- 重建运行态 Set；
- 重置不能跨刷新延续的 analyzing/loading 状态。

直接使用上游 `options.ts` 或 `normalizers/persistedState.ts` 会丢失或破坏这些语义。

### 3.2 per-account workspace 已经扩展

当前 `AccountWorkspace` 已保存：

- repositories / gists / releases / forks；
- 自定义分类结构；
- `subcategories` / `subcategoryOrder` / `repositoryOrder`；
- `classificationSchemes` / `classificationNavigation`；
- external discovery channels；
- GitHub List 映射与 sync mode。

这是 #424 最大的本地差异，因为上游 `accountWorkspacesUnchanged()` 的字段清单只认识上游自己的 workspace 字段。

审计还发现一个值得顺手补的当前边界：`workspaceHasData()` 目前只检查 repositories/gists/releases/forks/customCategories/categoryOrder 等，**没有把 `classificationSchemes`、`classificationNavigation`、`subcategories`、`subcategoryOrder`、`repositoryOrder`、external discovery channels 纳入“有数据”判定**。在账号切换/登录恢复路径上，这可能把只有分类结构但暂时没有 repo 的 workspace 误判为空。该问题不一定由 v0.8.6 引入，但分片迁移会把 workspace 正确性变成更关键的前提，建议在 Phase 1 一起修正并加测试。

### 3.3 Plugin V1.4 页面安全模型已比上游起点更强

GSM 当前插件页面已经有：

- 每页 session token；
- `event.source` / origin / token 校验；
- request id 去重；
- pending request 数量限制；
- 每分钟调用限流；
- 插件停用时 page session revoke；
- 账号 token 改变时失效；
- AI 调用确认和任务日志；
- Web Search 宿主确认；
- clipboard/download 主进程 host operation。

因此 #433 的正确迁移方式是增加 `network.request` capability，而不是把当前 `PluginPageViewer` 退回上游实现。

### 3.4 WebDAV 已有取消与未知结果保护

当前 GSM 通过 `electronProxy.ts` 的 `webdavRequest/webdavCancel` 做桌面请求，且上传路径已经明确考虑：桌面 PUT 被中断时结果未知，不应自动重放造成重复/覆盖风险。

#426 的“失败换网络栈”如果无条件套到 PUT/MKCOL 等变更请求上，会削弱这一契约。迁移必须按方法分类。

### 3.5 诊断系统已经承载本地更多敏感域

GSM 已有 renderer/backend logger、logSanitizer、DiagnosticLogsPanel，同时项目内还有：

- AGY CLI runtime；
- MCP bearer/config；
- HTML Reading + SMTP app password；
- safeStorage X auth；
- WebDAV credentials；
- proxy username/password；
- RPC secret；
- backend API secret；
- 本地 Agent / CLI stderr。

上游 #428 的 token/API-key 自动脱敏是基础，但“日志里没有 token”不等于“日志里没有隐私内容”。README、私有仓库 API response、邮件主题/正文、CLI stderr 都可能在没有 token 的情况下仍然敏感。

## 4. Git 与实施策略

### 4.1 不创建“伪全量升级”的 merge 历史

当前 GSM 对 v0.8.5 已经是 selective migration，而不是完整 merge。若现在把 v0.8.6 直接 merge，会同时再次引入 #414–#422 的全部上游路径，并产生大量“看起来历史已消费、实际按个人语义重写过”的混合状态。

```text
  +-- phase-4-plugin-network-insights
  +-- phase-5-info-card-readme-chat
  +-- phase-6-diagnostics
  +-- phase-7-deps-release-gates
```

实际可以是一条顺序 branch，每个阶段一个或多个提交；重点是**提交边界按能力域，不按 PR merge commit**。

### 4.2 上游代码提取规则

Codex 每处理一个 PR：

1. 先看 `git diff <merge>^1 <merge> --stat`；
2. 再看 `git diff <merge>^1 <merge> -- <相关文件>`；
3. 再看 `git show v0.8.6:<path>` 确认是否被后续 #434/#435 修改；
4. 最后在当前 GSM 中定位调用方；
5. 手工实现最终语义；
6. 移植能证明该语义的测试。

不要直接 `cherry-pick 7930e8d`、`5772a8e`、`5eb7bba`、`9bbc5a8` 等大型 merge commit。

### 4.3 #434 的正确拆分方式

#434 不是一个独立“功能”。应拆成：

- **Persistence fix packet**：大分片 idle 冷却/节流、UTF-8 大小统计、调度时重新判脏；随 #424。
- **WebDAV fix packet**：PROPFIND 检测与 fallback；随 #426。
- **Repo Insights fix packet**：Chart.js 最小化/resize race；随 #433。
- **Diagnostics fix packet**：fetch clone/abort、net tap、redaction/logger 稳定性；随 #428。

这样每个阶段落地时拿到的都是 v0.8.6 最终状态，不会先引入已知 bug 再等几阶段后修。

## 5. PR #424 + #434：分片持久化迁移深度设计

### 5.1 为什么应该迁

当前 `src/store/persistence/storage.ts` 的写入路径是：

```text
partialize whole state
  -> debounce 1s
  -> requestIdleCallback
  -> JSON.stringify(StorageValue whole object)
  -> indexedDBStorage.setItem(single key)
```

只要任意被持久化的 UI 配置变化，就会重新序列化全部 repositories/gists/releases/accountWorkspaces 等重数据。上游实测约 144MB，正是 #424 解决的目标。

上游最终方案的核心价值并不只是“多几个 IDB key”，而是以下完整不变量：

1. 大数据按 shard 拆分；
2. dirty shard 才 stringify；
3. 同一批 dirty shards + meta 在**一个 IndexedDB readwrite transaction** 中原子提交；
4. legacy 单键首次可读，首次完整 shard commit 后再退役；
5. meta 缺失可打捞 orphan shards；
6. 读取失败和“键不存在”严格区分；读取不完整时拒绝写盘，防止默认值覆盖磁盘真数据；
7. clear data 要清理主键及 `${name}#...` 派生键；
8. #434 对大 shard idle 写入增加最小 60 秒冷却，但 flush 立即写；
9. 小 shard 不被大 shard 冷却拖延。

这些都应当作为一个整体吸收。

### 5.2 当前 IndexedDB 层缺失的基础能力

GSM 当前 `src/services/indexedDbStorage.ts` 只有单键：

- `idbGet`
- `idbSet`
- `idbDelete`
- `indexedDBStorage.getItem/setItem/removeItem`

而 v0.8.6 的分片层依赖：

- 单事务 `idbSetMany`；
- 单事务 `idbGetMany`；
- `idbHasKey`；
- 派生键范围删除；
- `setStorageEntries()`；
- `getStorageItemStrict()` / `getStorageEntriesStrict()`；
- fallback authoritative marker；
- `removeLegacySnapshot()`；
- 事务 `onabort` 收敛。

因此 Phase Persistence 不能只新增 `shards.ts`；必须先升级 IndexedDB adapter。

### 5.3 上游 shard 不能原样使用

上游 v0.8.6 shard：

```text
core
repositories
gists
releases
forks
accountWorkspaces
trendingSnapshots
```

未知 partialize 字段会兜底进 `core`。对原项目这是安全兜底，但对 GSM 的双分类是性能陷阱：

- `classificationSchemes` 可能随仓库数量增长；
- 一个 scheme 中包含组织结构和 repository membership 投影；
- `subcategories` / `repositoryOrder` 可能随 repo 数增长；
- 如果全部掉进 core，切换主题/视图时依然可能 stringify 大量分类状态。

### 5.4 推荐 GSM shard 布局

建议增加一个明确的 `organization` shard：

| shard | 建议字段 | 原因 |
| --- | --- | --- |
| `core` | auth、theme、AI 配置、MCP、WebDAV config、视图偏好、active scheme、轻量过滤器等 | 小、常变 |
| `repositories` | `repositories` | 大数组 |
| `gists` | `gists`, `starredGists` | 大数组 |
| `releases` | `releases` | 大数组 |
| `forks` | `forks` | 大数组 |
| `organization` | `classificationSchemes`, `customCategories`, `hiddenDefaultCategoryIds`, `categoryOrder`, `subcategories`, `subcategoryOrder`, `repositoryOrder`, `defaultCategoryOverrides` | 组织结构可能很大，应与 UI core 隔离 |
| `accountWorkspaces` | `accountWorkspaces` | 每账号完整停车快照，可能最大 |
| `trendingSnapshots` | `trendingSnapshots` | 独立历史重数据 |

以下字段建议留 `core`，因为体积小且更新频繁：

- `activeClassificationScheme`
- `classificationNavigation`（若确认只是轻量导航状态）
- `collapsedSidebarCategoryCount`
- `categoryMatchMode`
- `categoryListIdMap`

如果后续测量发现 `classificationNavigation` 包含随 repo 增长的结构，再移动到 `organization`。不要凭名称决定，先用真实备份统计 JSON byte size。

### 5.5 organization shard 的原子性问题

Repository membership 当前既可能写在 repository 对象，也可能由 classification scheme 投影表示。迁移时必须确认一次“分类应用”会同时脏哪些 shard。

好消息是上游 `setStorageEntries()` 会把**本轮所有 dirty shards**放进同一个 IDB transaction，所以 `repositories + organization` 同轮改变时可以原子落盘。

坏消息是如果某个分类操作原地修改了对象/数组，引用判脏可能看不出来，导致只写其中一个 shard。

所以必须把“不可变更新”升级为迁移硬门禁。

### 5.6 不可变更新审计

上游 `findDirtyShards()` 对重 shard 使用字段引用判脏。审计时在本地服务代码里能找到 `.push` / `Object.assign` 等操作，例如 AI 分类结构构建函数，但部分发生在 `clone(expected)` 或 trial snapshot 上，并不等于直接修改 Zustand live state。

Codex 不能只用 regex 看到 `.push` 就认定 bug。正确审计方法：

1. 从所有会修改 `repositories`、`classificationSchemes`、`customCategories`、`subcategories`、`repositoryOrder`、`accountWorkspaces` 的 store action 开始；
2. 确认传给 `set()` 的顶层字段引用一定变化；
3. 确认嵌套 scheme/workspace 改动也会产生新的外层 map/object；
4. 为每类关键 action 加“修改后 shard 被判 dirty”的测试；
5. 测试不要仅断言 UI 变了，要断言 reload 后数据仍在。

### 5.7 AccountWorkspace dirty-check 必须扩展

上游 v0.8.6 `WORKSPACE_REFERENCE_FIELDS` 只认识：

```text
repositories, gists, starredGists, releases, forks,
customCategories, categoryOrder, readReleases, readForks,
releaseSubscriptions, hiddenDefaultCategoryIds
```

`WORKSPACE_VALUE_FIELDS` 只认识：

```text
lastSync, selectedGistCategory, releaseSourceSettings,
defaultCategoryOverrides, categoryListIdMap, syncMode, syncModeConfigured
```

GSM 至少还要覆盖：

- `classificationSchemes`
- `classificationNavigation`
- `subcategories`
- `subcategoryOrder`
- `repositoryOrder`
- `externalDiscoveryChannels`

推荐：

- 大数组/大对象且 store 保证 immutable 的放 reference fields；
- 归一化经常重建的小对象放 value fields，用稳定 JSON/value equality；
- 测试枚举 `AccountWorkspace` 所有持久字段，要求每个字段恰好落入 reference/value 一类，防止未来加字段后静默漏写。

### 5.8 Normalizer 引用稳定性

上游 #424 同时改 `persistedState.ts` 和 `trendingSnapshots.ts`，原因不是业务需求，而是**归一化若无条件新建等价对象，会让 dirty-check 永远认为 shard 变了**。

GSM 的 normalizer 更复杂，因此 Codex 要逐项检查：

- `normalizeAccountWorkspaces`
- `normalizeClassificationSchemes`
- `normalizeRepositoryOrganization`
- `normalizeTrendingSnapshots`
- `normalizeExternalDiscoveryChannels`

目标是：内容没有变化时尽量保留已有引用；如果无法保留，则该字段不能使用纯 reference dirty-check，必须提供专用 equality。

### 5.9 Store version 与 shard format 不应混为一谈

当前 persistence version 是 17。分片属于**存储布局**变化，已有 `PERSISTENCE_SHARD_FORMAT` 独立版本，不需要因为“改成 shards”就机械把 Store 17 升到 18。

建议：

- 如果逻辑 state schema 不变，只改布局：Store version 继续 17，shard format 1；
- 如果这次顺带修复 workspace/schema，需要强制运行新的 Zustand `migrate`：再升到 18，并明确写 v17→v18 migration；
- 不允许“先把 version 改 18 但 migrate 没有对应语义”。

### 5.10 数据迁移测试矩阵

必须覆盖：

1. v17 legacy 单键 → 首次启动 → 正确 hydrate；
2. 首次修改小 core → 全 shard 首次迁移 → reload 数据完整；
3. 第二次只改 theme → 只写 core；
4. 修改一个 repository → repositories dirty；
5. 修改 purpose classification → organization dirty；
6. 修改 parked account 的 technology scheme → accountWorkspaces dirty；
7. legacy + 部分 shard 并存 → 新 shard 覆盖同字段，legacy 补缺失；
8. meta 缺失但 shard 在 → orphan salvage；
9. IDB read transaction 失败 → `hydratedIncomplete` → 禁止写盘；
10. IDB batch write 中途失败 → 原子回滚；
11. localStorage fallback 被置为 authority 后 reload 不回滚到 IDB 旧值；
12. clear all → 主键、meta、所有 shard、fallback marker 都消失；
13. `pagehide` / hidden flush 绕过 60s 大 shard throttle；
14. 大 organization/accountWorkspace shard 冷却时，core 改动仍立即保存；
15. 数据管理备份/恢复后双分类结构、repo order、账号 workspace 全部一致。

### 5.11 文件级建议

**新增/主要重写：**

- `src/store/persistence/shards.ts`：以 v0.8.6 为底，加入 GSM `organization` shard 与 workspace 字段清单。
- `src/store/persistence/storage.ts`：按 v0.8.6 最终版移植 #424 + #434，但保留现有 `flushAppStorePersistence()` 外部契约。
- `src/store/persistence/storage.test.ts`：移植上游测试并加双分类/workspace 用例。

**适配：**

- `src/services/indexedDbStorage.ts`
- `src/store/normalizers/persistedState.ts`
- `src/store/helpers/accountWorkspace.ts`
- `src/utils/trendingSnapshots.ts`
- `src/components/settings/DataManagementPanel.tsx`
- `src/store/useAppStore.test.ts`

`DataManagementPanel` 的“清空数据”要等待真实 derived-key 删除完成；不要只依赖 Zustand `persist.clearStorage()` 的返回语义。

### 5.12 #424 还包含一个值得独立移植的 README 滚动性能 hunk

#424 第一父 diff 还修改了 `src/components/ReadmeModal.tsx`。它没有改变持久化格式，而是把滚动进度条对 `scrollTop/scrollHeight/clientHeight` 的同步布局读取合并到 `requestAnimationFrame`，并在 unmount 时按实际调度 API 正确取消 rAF/timeout。

## 6. PR #426 + #434：WebDAV 与统一主进程网络

### 6.1 应吸收的核心能力

上游新增 `electron/mainFetch.js`，解决两类根因：

1. Node/undici 的 `TypeError('fetch failed')` 隐藏真实 cause；
2. Node 直连在系统代理、自签名证书等环境失败，而 Chromium `net.fetch` 可用。

值得完整吸收的 helper 语义：

- 展开 `error.cause` / `AggregateError`；
- 返回 `causeCode`, `causeMessage`, `timedOut`；
- 多网络栈共享**总超时预算**；
- HTTP 4xx/5xx 默认视为有效 response，不因业务错误切换网络栈；
- 只有网络层 throw 才 fallback；
- 手动重定向，跨 origin 剥离 `Authorization` / `Cookie`；
- 丢弃未使用 response body，归还连接；
- main IPC 失败返回结构化错误。

### 6.2 `undici` 版本是功能正确性，不只是依赖升级

当前 GSM 根 `undici` 是 `7.29.1`，v0.8.6 是 `^8.11.2`。

上游新增 `outboundFetchGate.test.js` 明确防止：Electron/Node 内置 fetch 使用的 undici handler 协议，与 npm `undici@8` 的 `ProxyAgent` 混用导致 `UND_ERR_INVALID_ARG`。

因此迁移 #426 时必须一起决定：

- `const { fetch: undiciFetch, ProxyAgent } = require('undici')` 同源；
- 带 `dispatcher` 的请求只调用 `undiciFetch`；
- 禁止主进程裸 `fetch()` 与 npm `ProxyAgent` 混用；
- 对 `net.fetch` 继续使用 Chromium 栈。

这是 #423 依赖迁移中最明确的“必须升级”项。

此外，复核当前 GSM 源码后发现，这个风险模式**不是未来才可能出现，而是当前代码里已经存在**：

```text
electron/main.js:378     getFetchDispatcher() 返回 npm `undici` 的 ProxyAgent
electron/main.js:415-423 X 页面请求使用全局 fetch(...) + dispatcher
electron/main.js:507-512 X GraphQL 请求使用全局 fetch(...) + dispatcher
electron/main.js:1036    WebDAV 路径使用 require('undici').fetch(...) + 同源 dispatcher（这是正确配对）
```

当前 `undici@7.29.1` 下不能武断声称这两条 X 路径“现在一定会炸”，但它与上游 `outboundFetchGate.test.js` 专门防止的混用模式同构；一旦按 #426/#423 把 npm undici 升到 8.x，这会变成迁移成败的直接前置条件。因此应在正式进入 Phase 2 前先完成一个很小的去风险动作：凡是携带 `dispatcher` 的请求都统一使用同一个 npm `undici.fetch`，并补 gate test，禁止未来再次出现“全局裸 fetch + npm ProxyAgent”。

### 6.3 必须保留 GSM 的变更请求不重放规则

上游 `fetchAcrossStacks()` 是通用 helper，但 GSM 不能因此把所有 WebDAV 方法都自动 fallback/retry。

建议按请求性质：

**可安全跨栈重试：**

- GET
- HEAD
- PROPFIND
- OPTIONS

**必须谨慎：**

- PUT
- DELETE
- MOVE
- COPY
- MKCOL

这些请求如果 Node 栈在“服务端已经处理，但客户端还没收到响应”的时刻断线，再由 Chromium 重放，可能产生不可逆副作用。现有 GSM 的“桌面 PUT 结果未知则不自动重放”应保留并扩展为明确策略表。

### 6.4 #434 的连接探测修复

上游最终版改进 WebDAV connectivity probing：

- 优先 `PROPFIND Depth: 0`；
- 某些服务器不支持/拒绝 HEAD 时不误判离线；
- 解析 `207 Multi-Status`；
- HEAD/PROPFIND 在同一总 timeout budget 内收敛。

这一修复应随 #426 一起落地。

### 6.5 当前文件冲突策略

- `electron/main.js`：**只接入 helper 和 IPC 逻辑，不整文件替换**。这里还有 AGY、HTML Reading、插件、X/Telegram 等本地接线。
- `electron/preload.js`：保留现有 API，增加/调整结构化错误字段，不删本地桥。
- `src/services/electronProxy.ts`：保留 requestId + cancel；扩展 failure result 类型。
- `src/services/webdavService.ts`：函数级重构 transport selector，不覆盖本地上传保护。
- `src/services/xTweetService.ts`：如果吸收 #426 对 X 的 stack fallback，要单独验证 X 当前本地 auth/proxy 逻辑，不把 WebDAV 策略机械复用。

### 6.6 验证用例

- DNS `ENOTFOUND` 能展示根因；
- `ECONNREFUSED` 能展示地址/错误码；
- Node 栈网络失败后 Chromium 成功；
- Node 得 401 时不 fallback；
- 总 timeout 不因为两个栈翻倍；
- 跨域 redirect 不泄漏 Basic Authorization；
- PROPFIND-only 服务器被识别为在线；
- PUT 桌面栈未知结果不自动重放；
- cancel 后主/渲染两边都收敛；
- 使用 proxy dispatcher 时没有 `UND_ERR_INVALID_ARG`。

## 7. PR #427：Plugin Marketplace 与可维护 Sources

### 7.1 功能价值

这是从“插件能力存在”走向“插件可以被普通用户发现、安装、升级、卸载”的关键产品层，值得迁移。

上游实现不是简单下载 zip，安全设计包括：

- 只接受 GitHub HTTPS repo/tree source；
- 默认分支/指定分支解析后，单次操作固定到 commit SHA；
- GitHub API 枚举目录；
- source/package 文件数与总大小上限；
- 下载并发限制；
- Windows 保留设备名/危险路径拒绝；
- 禁止 path traversal、绝对路径、异常目录；
- 安装前后 manifest identity/version 一致性校验；
- staging directory；
- 最终替换使用原子目录 rename；
- 更新失败回滚旧版本；
- 权限变化后不自动恢复 enabled；
- 官方 revoked/blocked 仍做最终 gate。

这些安全属性应尽量整体保留。

### 7.2 GSM 现有 Registry 不应删除

当前 `PluginRegistrySection.tsx` 明确设计为：

> 只读对照：显示已安装插件的 update/revoked/blocked；不下载、不安装、不自动停用。

这不是 Marketplace 的竞争实现，而是**信任/治理层**。上游 `pluginMarketplace.js` 自己也把“官方静态注册表的撤销/拉黑”视为独立终审。

推荐最终结构：

```text
Plugin Settings
  ├─ Marketplace / Sources：发现、安装、更新、卸载
  ├─ Installed Plugins：启停与权限
  └─ Registry Trust Status：官方版本/撤销/拉黑/权限 diff
```

### 7.3 当前缺少 `replaceFromDirectory`

GSM 当前 `pluginManager.js` 有 `installFromDirectory()` 和 `uninstall()`，但没有上游 #427 的 `replaceFromDirectory()`。

这个函数必须移植，因为更新的正确性依赖它：

1. 记录 previous plugin state；
2. 停 Worker；
3. 把旧目录 rename 到 backup；
4. 安装新目录；
5. 失败则恢复 backup；
6. 如果旧插件已启用且权限未变，重新 activate；
7. 权限变了则保持 disabled，等用户重新确认。

GSM 还应加一个本地强化：**replace 开始前主动 revoke 该插件所有 page session**。否则已经打开的旧 iframe 有机会在目录替换期间继续持 session token 发 capability request。

### 7.4 Marketplace IPC 接线原则

需要吸收：

- `electron/plugins/pluginMarketplace.js`
- `electron/plugins/pluginMarketplaceState.js`
- main IPC handlers
- preload API
- `src/services/pluginMarketplaceService.ts`
- `PluginMarketplaceDialog`
- `PluginSourcesDialog`
- `PluginUninstallDialog`

但 `electron/main.js` / `preload.js` 必须 union wiring，禁止覆盖。

### 7.5 安装和启用必须继续分离

上游产品文案强调：安装只是把文件写本地；启用前展示权限。

GSM 应继续保持：

```text
Marketplace Install
    ↓
plugin disabled on disk
    ↓
user toggles Enable
    ↓
permission prompt
    ↓
host enable
```

不能把“一键安装”理解为“一键安装并执行”。

### 7.6 自定义源与供应链风险

自定义 GitHub 源能力本身应保留，但 UI 要表达清楚：

- “source 是发现位置，不等于官方信任”；
- 安装包 commit SHA 固定只保证下载过程一致，不证明代码可信；
- 更新后新增 permission 必须重新确认；
- Registry blocked/revoked 应在安装和更新最终提交前复核；
- Marketplace cache 不应绕过最新撤销状态。

### 7.7 测试矩阵

- repo root / tree path source 解析；
- 默认 branch；
- branch 在 browse/install 间改变时仍 pin 同一 SHA；
- manifest id/version 被远端替换时拒绝；
- `../`、绝对路径、Windows device name 拒绝；
- 超文件数/超体积拒绝；
- 已装插件 update 成功；
- update 中安装失败 → 旧目录/旧状态恢复；
- update 后权限增加 → disabled；
- update 权限不变且之前 enabled → Worker 重新启动；
- replace 时旧 page session 失效；
- revoked/blocked 不能最终安装；
- uninstall 保留数据 / 删除数据两种语义；
- source 编辑、单源刷新、删除不影响已安装插件。

## 8. PR #433 + #434：V1.5 `network.request` 与 Repo Insights

### 8.1 正确架构：扩展现有 V1.4，不替换

推荐调用链：

```text
plugin iframe
  -> PluginPageViewer verifies source/origin/session token/request limits
  -> main pluginPageBridge validates method/host/path/query
  -> capabilityRouter checks network:<host> permission
  -> renderer host network executor adds GitHub auth under host control
  -> response is size-limited/sanitized and returned to page
```

GSM 已有的 session/dedupe/rate-limit/revoke 必须全部留在第一层。

### 8.2 上游 allowlist 应完整移植

v0.8.6 只允许 host：

```text
api.github.com
```

路径是明确模板，例如：

- `/repos/{owner}/{repo}`
- `/stats/commit_activity`
- `/stats/participation`
- `/stats/code_frequency`
- `/contributors`
- `/languages`
- `/releases`
- `/pulls`
- `/tags`
- `/stargazers`
- `/community/profile`
- `/security-advisories`
- `/users/{login}`

校验还应保留：

- path 不接受 `?` / `#` / `\` / whitespace；
- 拒绝 `.`/`..`；
- owner/repo segment 正则；
- query 只允许 `per_page`, `page`, `state`；
- 页码/页大小有上限。

主进程与渲染端应有同一份行为清单，并用 parity test 防漂移。

### 8.3 网络 executor 的必须属性

上游 `usePluginNetwork` 的值得保留点：

- GitHub token 由宿主持有，不传给插件；
- GET-only；
- redirect error；
- no-referrer；
- 15s timeout；
- success response 最大约 4 MiB；
- error body 更小预算；
- streaming 过程中执行 size cap，而不是读完再检查；
- abort support；
- request 前后重新做 authorization/session 状态检查。

GSM 应把 `network.request` 的 AbortController 加入当前 page session 生命周期：页面关闭、插件停用、账号切换时终止在途请求。

### 8.4 私有仓库数据是本地需要额外澄清的安全边界

上游声明“token 不离开机器”是成立的，但插件 iframe 本身运行的是第三方插件代码。若宿主使用用户 token 请求 GitHub，返回的**私有仓库 metadata 本身**会进入插件代码。

因此 GSM 推荐增强：

1. 权限文案不要只写“访问 api.github.com”，而要明确“使用当前 GitHub 身份发起白名单只读 API 请求”；
2. 对已知本地 private repository，如果插件只有 `repositories:read` 而没有 `privateRepositories:read`，不应返回私有 response；
3. 最保守实现是：无 `privateRepositories:read` 时对 network request 使用无 token/public 请求；需要私有 API 时必须额外 permission；
4. Repo Insights 官方示例如果要支持私有仓库，应在 manifest 和 prompt 中明确申请私有权限，或明确只支持公开指标。

如果为了与上游完全一致先不做第 2/3 点，也必须在迁移记录中登记为 residual risk，而不能把“token 没暴露”写成“私有数据绝不暴露”。

### 8.5 Repo Insights 应作为示例插件落地，不侵入 core Store

优点：

- 页面逻辑、Chart.js、AI 近期总结都封装在 `examples/plugins/repo-insights`；
- 宿主只提供通用网络能力；
- 不需要给 GSM Store 再塞 repo insight cache；
- 插件可以独立升级。

建议直接以 v0.8.6 最终 sample 为基线，包括 #434 的 Chart.js 最小化 race 修复。

### 8.6 指标解释边界

Repo Insights 的一些数据不是绝对事实：

- Bus Factor 是启发式估算；
- GitHub stats endpoint 可能先返回 202；
- security advisories 可能因 repo/token 权限返回 403；
- stargazer history 并非所有仓库都能获得完备历史；
- 贡献者统计对 squash/bot 有偏差。

UI 应把“未知/不可用”和“差”区分，不能把权限不足当作健康分扣分。

### 8.7 AI Recent Summary

插件会把近期 PR、release notes、提交统计拼成 prompt，通过现有 `ai.generate`。

GSM 现有 AI confirmation/task logging 应继续生效：

- prompt 在发送前经过宿主确认；
- page 不能直接拿 API key；
- AI output 只返回对应 session；
- 关闭页面要 abort/忽略过期结果；
- 诊断日志不要记录完整 release body/prompt，最多记录长度、模型、request id。

### 8.8 文件级迁移

**新增：**

- `src/plugins/networkTargets.ts`
- `src/plugins/networkTargets.test.ts`

**适配：**

- 对应 tests
- `src/components/PluginPageViewer.tsx`

`pluginAccountTag` 在 GSM 中最好优先使用稳定 GitHub user id 做 cache namespace；如果为了兼容上游示例仍使用 token-derived tag，要确认 token rotate 只导致 cache miss，不导致跨账号缓存串用。

## 13. PR #423 与 #430：依赖和 CVE 的正确吸收方式

### 13.1 为什么不能复制 lockfile

当前 GSM 与 v0.8.6 的依赖状态不是“旧→新”单向关系：

- root Electron/Vite/Vitest 已基本与 v0.8.6 同档；
- root `undici` 仍是 7.29.1；
- server 本地部分工具甚至已经比上游更新；
- 本地还有上游没有的 runtime dependency 和 scripts。

所以 #423 的正确操作是做 manifest-level reconciliation，再在 GSM 自己的树上 `npm install` 生成 lock。

### 13.2 明确需要升级的依赖

为了 #426，`undici` 应升级到与 v0.8.6 一致的 `^8.11.2` 或审计时更精确的兼容版本，并运行 outbound fetch gate。

其他依赖逐项比较：

- 如果 GSM 已更新，保留兼容的更高版本；
- 如果上游只是 dev tool patch，而本地功能不依赖，不强制降级/覆盖；
- cloudflare-worker/server 只吸收与本次功能或安全有关的版本。

#423 的 manifest 级实际变化只有三项：

- root `undici`: `^7.29.1` → `^8.11.2`；
- server `morgan`: `^1.12.0` → `^1.12.1`；
- cloudflare-worker `wrangler`: `^4.133.0` → `^4.146.0`。

当前 GSM 重新核对结果是：server 已经是 `morgan ^1.12.1`，因此该项已经等价吸收；root 仍是 `undici 7.29.1`，需要随 #426 升级；cloudflare-worker 仍是 `wrangler ^4.133.0`，但与本次桌面/插件主链没有直接依赖，应在最终依赖阶段单独验证 Worker build 后再升级。

### 13.3 #430 的 CVE 处理

审计时当前 `npm ls http-cache-semantics --all --depth=8` 为空，当前 lock 中也未发现该包。

因此：

1. 不直接往 GSM 添加一个没有调用方的 `http-cache-semantics` 依赖；
2. 完成 #423/undici 等实际依赖升级并重新生成 lock；
3. 再执行 `npm ls http-cache-semantics --all`；
4. 若新树里出现 `<4.3.0`，再通过上游同等依赖更新/override 升到安全版本；
5. 跑 `npm audit` 并记录结果。

这才是真正吸收 #430 的安全意图。

### 13.4 #430 的测试加固不能因为 CVE 不命中而全部跳过

#430 第一父 diff 除 `package-lock.json` 把 `http-cache-semantics 4.2.0` 升到 `4.3.0` 外，还修改了 16 个测试文件。已核实的典型改动包括：

- `pluginManager.test.js`：创建 symlink 不可用时使用 `t.skip()`，同时显式 `return`，避免 Node `test` 的 skip 标记后继续执行测试体；
- `MarkdownRenderer.test.tsx`：不再读取源码文本判断 Safari lookbehind，而是导出并直接测试 `MATH_PATTERN`；同时用 passthrough mock 证明普通文档不会触发 math 动态 import；
- `aiRequestLimiter.test.ts`：扩大真实时钟窗口，降低 CI event-loop stall 造成的偶发超发误判；
- `abortUtils.test.ts`：显式断言 abort 后 pending timer count 已清零；
- 其余 plugin/runtime/server parity/release/webdav/store tests 也包含环境隔离与兼容性调整。

这些不是生产行为升级，但能提高迁移后测试门禁的可信度。Codex 应按以下规则处理：

1. 如果 GSM 当前测试仍有同样的脆弱写法，移植对应 hunk；
2. 如果本地测试已经因新架构重写，以“相同不变量”重新实现，不覆盖当前 fixture；
3. 不为了让测试通过而降低断言强度；
4. #430 测试 hunk 可以在对应功能阶段顺手吸收，不必等到 Phase 7 一次性做。

### Phase 0 — 冻结与恢复点

建议固化成可执行序列，而不是只写“先备份”：

1. 对当前 tracked + untracked 做三分：
   - A 类：正式功能源码/文档，进入迁移前 checkpoint；
   - B 类：验证产物、临时日志、fixture，单独归档并记录路径；
   - C 类：误生成的 build/cache，确认无价值后清理或补 `.gitignore`。
2. 为 A 类形成 **WIP checkpoint commit**。它不是发布成果，只是为了让当前 8.5 后个人开发可被完整恢复。
3. 沿用既有命名习惯建立 recovery tag，例如 `recovery/pre-v0.8.6`，不要发明另一套恢复命名体系。
4. 保存当前用户数据/应用备份与 legacy Store 样本。
5. 在任何 v0.8.6 代码进入之前采集 before 基线：build、全测试、Electron plugin/WebDAV、server build/test、lint error/warning 数。
6. 固定 `v0.8.6` SHA 和本次不包含 #436 的边界。
7. 从 checkpoint 建立干净 upgrade worktree/branch，后续迁移只在该隔离分支做。

交付至少包括：checkpoint commit/tag、A/B/C 清单、before 日志、当前个人功能清单、真实数据备份位置说明、固定 `v0.8.6` SHA。

退出条件：能在不丢当前个人工作情况下创建干净 upgrade worktree/branch。

## 21. 数据恢复与回滚策略

Persistence Phase 必须在真实个人数据上执行前准备：

1. 导出应用 backup；
2. 复制 IndexedDB profile 或使用已有应用备份机制保存 legacy snapshot；
3. 保存 v17 单键样本；
4. 迁移后不要立即删除外部 backup；
5. 只有在“legacy→shards→reload→修改→reload”两轮成功后，才把新格式视为可靠。

应用内部会在成功全 shard commit 后退役 legacy 单键，但外部人工备份应保留到版本验收完成。

如果 migration build 出现严重问题，回滚旧应用时要注意：旧版本不知道 `${name}#shard:*`，但 legacy 单键可能已被新版本删除。**因此不能把“应用内部自动保留 legacy”当成跨版本 downgrade 方案。**发布前应有明确 backup/export 恢复路径。

## 27. 审计结论

v0.8.6 是一个很值得吸收的上游版本，但对当前 GSM 来说它已经不能被理解为“版本升级”，而应视为四个架构能力包和若干 UX 修复的**语义移植工程**。

最关键的取舍不是“ours/theirs 选哪个”，而是：

- 用上游成熟的 shard/transaction/recovery 模型，承载 GSM 更复杂的双分类数据；
- 用上游 Marketplace/Network 能力，承载 GSM 更强的插件 session 权限模型；
- 用上游多网络栈和诊断能力，保留 GSM 对未知副作用、secret 和私有正文更严格的安全边界；
- 用上游最终 sample/UI，避免把 core 架构退回上游较简单状态。
